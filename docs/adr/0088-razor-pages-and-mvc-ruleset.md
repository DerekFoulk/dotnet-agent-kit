# ADR-0088: Razor Pages and MVC ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

Razor Pages and MVC apps are ASP.NET Core apps that render HTML on the server from Razor views or pages. Its `project-types.yml` entry is `razor-pages-mvc` (ASP.NET Core Razor Pages and MVC), and its docs start at <https://learn.microsoft.com/aspnet/core/razor-pages/>.

ADR-0082 makes every rule name the project types it applies to. ADR-0084 gives an app only the common ruleset plus the rulesets of its project types. This ADR records the ruleset for `razor-pages-mvc` (ASP.NET Core Razor Pages and MVC), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/aspnetcore.md`):

- <https://learn.microsoft.com/aspnet/core/razor-pages/>: overposting; layout location (ASP-011, ASP-014).
- <https://learn.microsoft.com/aspnet/core/razor-pages/razor-pages-conventions>: avoid setting route Order (ASP-014).
- <https://learn.microsoft.com/aspnet/core/mvc/views/overview>: view models with little or no behavior; no Raw on user input (ASP-013).
- <https://learn.microsoft.com/aspnet/core/mvc/views/partial>: partial views guidance (ASP-013).
- <https://learn.microsoft.com/aspnet/core/mvc/controllers/filters>: prefer authorization policies and middleware over custom filters (ASP-010).
- <https://learn.microsoft.com/aspnet/core/mvc/models/model-binding>: view models over [Bind]; custom binders (ASP-011).
- <https://learn.microsoft.com/aspnet/core/security/anti-request-forgery>: AutoValidateAntiforgeryToken for cookie apps (ASP-005).
- <https://learn.microsoft.com/aspnet/core/fundamentals/app-state>: session state: nothing sensitive, keep the site working without it (ASP-004).
- <https://learn.microsoft.com/aspnet/core/security/authentication/configure-oidc-web-authentication>: confidential client, code flow, PKCE (ASP-021).
- <https://learn.microsoft.com/aspnet/core/performance/caching/response>: response caching only for user-independent content (ASP-009).
- <https://learn.microsoft.com/aspnet/core/mvc/models/file-uploads>: safe handling of uploaded files (ASP-006).

Razor Pages and MVC apps share the web rules with Web APIs and Blazor. Two rules name `razor-pages-mvc` alone, ASP-013 (MVC views) and ASP-014 (Razor Pages layout and routes), and web UI accessibility (UI-001 to UI-003) applies.

## Options

### Option 1: A ruleset for ASP.NET Core Razor Pages and MVC

- **Trade-offs:** An app of this type gets the common rules plus the rules that name `razor-pages-mvc`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `projectTypes` list per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `projectTypes` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a desktop app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `razor-pages-mvc` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the project-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

- [API-001](../standards/api-design.md) (proposed): An app's API style is chosen in its plan: an HTTP API with Minimal APIs by default; gRPC, SignalR, controllers or GraphQL only where a Microsoft page recommends that style for the app's scenario (API-008) or the owner asks for it by name, and the plan says which.
- [API-008](../standards/api-design.md) (proposed): For a new ASP.NET Core HTTP API, Minimal APIs are recommended; consider controller-based APIs where the app needs what controllers provide, such as model binding extensibility, advanced validation, application parts or the application model, or OData. gRPC is well suited to microservices, point-to-point real-time communication, polyglot and network-constrained environments, and inter-process communication; other frameworks are recommended over gRPC for browser-accessible APIs and for broadcasting real-time messages, where SignalR is a useful framework.
- [API-002](../standards/api-design.md) (accepted): Every HTTP API error response is Problem Details (RFC 9457): AddProblemDetails, UseExceptionHandler and UseStatusCodePages; a client error such as malformed input stays a 400 in every environment, and outside Development a 500 never carries the exception's message or stack.
- [API-003](../standards/api-design.md) (accepted): An HTTP API describes itself with the built-in OpenAPI document (Microsoft.AspNetCore.OpenApi) and typed results; the document, and any UI for it such as Scalar or Swagger UI, is mapped in Development only; a contract test snapshots the document, so every change to the API shows in review.
- [API-004](../standards/api-design.md) (accepted): Every HTTP endpoint that lists a collection pages it in the data store, in a deterministic order, with limit (default 25, at most 100) and offset (at most 10,000) query parameters, and answers an object with the page's items and a nextLink to the next page, null on the last page or the last one the offset cap allows.
- [API-005](../standards/api-design.md) (proposed): An HTTP API isn't versioned until its first breaking change to a contract that another app or a released client depends on; that change gets an ADR that picks how versions are told apart (URI, query string or header) and the package, a new version, and the earlier version stays until its callers move.
- [API-007](../standards/api-design.md) (accepted): An HTTP API follows HTTP's semantics as Azure's API design guidance sets them out: base resource URIs on nouns and not verbs where possible, and avoid verbs in URIs to represent operations; a POST that creates a resource synchronously should return 201 Created and identify the resource in the Location header; GET, HEAD, PUT and DELETE must be idempotent; and for work that takes time, consider an asynchronous method, which should return 202 Accepted with the status endpoint's URI in the Location header, whose status endpoint should return 303 See Other with the new resource's URI in a Location header once the work has created one.
- [API-009](../standards/api-design.md) (accepted): OpenAPI user interfaces (Swagger UI, ReDoc, Scalar) should only be enabled in development environments.
- [API-010](../standards/api-design.md) (accepted): In non-development environments, use the exception handler middleware to produce an error payload. Don't enable the Developer Exception Page unless the app is running in the Development environment, and don't share detailed exception information publicly when the app runs in production.
- [API-011](../standards/api-design.md) (accepted): Implement pagination for an endpoint that returns a collection: use limit and offset query parameters with meaningful defaults, such as limit=25 and offset=0, and consider an upper limit on the number of items returned. Apply pagination in the data store, not after loading the entire collection, with a deterministic sort order; include a next-page link or continuation token in the response, omitted or null on the last page; and for a large or frequently changing collection, evaluate cursor-based pagination.
- [API-012](../standards/api-design.md) (proposed): Support versioning in the API contract: when you introduce a breaking API change, introduce a new API version, continue to support the previous version, and let clients select which version to call. Make API changes backward compatible when possible.
- [API-013](../standards/api-design.md) (accepted): An HTTP API's URIs name a collection with a plural noun, and use a verb sparingly, only for an operation that isn't a resource.
- [ARC-001](../standards/architecture.md) (accepted): Web apps use Clean Architecture in one deployable app; each distinct business area is a module with Domain, Application, Infrastructure, Presentation and Contracts projects, and Application code is grouped by feature; a project can deviate by ADR.
- [ARC-002](../standards/architecture.md) (accepted): Modules talk to each other only through their Contracts projects; a module never reads or writes another module's tables, and an app never shares its database with another app.
- [ARC-016](../standards/architecture.md) (proposed): For a non-trivial monolithic ASP.NET Core application, Clean Architecture is the most appropriate way to structure it: the Application Core holds the business model and the abstractions for infrastructure, Infrastructure implements them, and the UI layer interacts with infrastructure strictly through interfaces defined in the Application Core.
- [ASP-001](../standards/aspnetcore.md) (proposed): Avoid the service locator pattern, stateful static classes and members, and direct instantiation of dependent classes within services. Prefer constructor parameters over resolving services from RequestServices, and never dispose a service the container resolved.
- [ASP-002](../standards/aspnetcore.md) (proposed): Never store passwords or other sensitive data in configuration provider code or in plain text configuration files, and don't use production secrets in development or test. Group related hierarchical configuration with the Options pattern (recommended). Don't store a production connection string in an environment variable (recommended against).
- [ASP-003](../standards/aspnetcore.md) (proposed): Set minimum log levels in configuration, not in C# code, and don't specify them with filter functions in code. Don't write log messages directly to a slow data store, such as SQL Server, in a Log method.
- [ASP-004](../standards/aspnetcore.md) (proposed): Don't store sensitive data in session state, and keep the site working without the session data: store critical data in the user database and cache it in session only as a performance optimization. SignalR apps shouldn't use session state. Never put sensitive data in a query string, and always revalidate data read back from hidden fields.
- [ASP-005](../standards/aspnetcore.md) (proposed): Never change state on a GET request (a best practice). For browser apps that use cookies, use AutoValidateAntiforgeryToken broadly outside API scenarios (recommended). Don't disable CSRF protection on browser-accessible endpoints that rely on cookies for authentication.
- [ASP-006](../standards/aspnetcore.md) (proposed): Handle uploaded files safely: never use a client-supplied file name to save a file to physical storage, never grant execute permission on the upload location, set a maximum size limit, don't persist uploads in the same directory tree as the app, and check the file's extension against a list of permitted extensions (should).
- [ASP-007](../standards/aspnetcore.md) (proposed): Don't store files that require authorization in wwwroot and rely only on MapStaticAssets().RequireAuthorization() to protect them. Disable directory browsing in production (highly recommended). Don't rely on file extension filtering to protect private files.
- [ASP-008](../standards/aspnetcore.md) (proposed): Write and test apps to never depend on cached data: always have a fallback that fetches the data. Don't insert external input into the cache, and avoid external user input directly in cache keys. Don't cache user-specific data that other users' requests may retrieve.
- [ASP-009](../standards/aspnetcore.md) (proposed): Enable HTTP response caching only for content that doesn't change based on a user's identity or whether a user is signed in. Mark responses with content for authenticated clients as not cacheable so the response caching middleware doesn't store and serve them.
- [ASP-010](../standards/aspnetcore.md) (proposed): In MVC and controller-based APIs, prefer authorization policies (or a custom authorization policy) over a custom filter, and prefer middleware for exception handling. Don't throw exceptions within authorization filters. Avoid filters used purely for logging.
- [ASP-011](../standards/aspnetcore.md) (proposed): Protect against overposting with view models rather than the [Bind] attribute (recommended). Don't use [BindProperty] on models containing properties the client shouldn't change. Don't apply [FromBody] to more than one parameter per action method. Create a type converter or use TryParse for a simple string-to-type conversion that needs no external resources (recommended).
- [ASP-013](../standards/aspnetcore.md) (proposed): In MVC views, use POCO view models with little or no behavior (recommended). Avoid HtmlHelper.Raw with user input. Don't use partial views for common layout elements or where complex rendering logic or code execution is needed. Render partial views asynchronously: the synchronous Partial and RenderPartial helpers aren't recommended.
- [ASP-014](../standards/aspnetcore.md) (proposed): In Razor Pages apps, put the layout file in Pages/Shared, not Views/Shared (recommended). Avoid setting route Order in production apps, and avoid depending on an established route processing order where possible.
- [ASP-015](../standards/aspnetcore.md) (proposed): Don't use route constraints for input validation: invalid input should produce a 400 Bad Request with an appropriate error message, not the 404 a failed constraint gives. SEC-010 and API-006 say how input is validated.
- [ASP-016](../standards/aspnetcore.md) (proposed): Never suppress the warnings ASP0003, ASP0004, ASP0006, ASP0008, ASP0009, ASP0010 and BL0005, and avoid the RenderTree types in user code (not recommended).
- [ASP-021](../standards/aspnetcore.md) (proposed): Web apps that sign users in with OpenID Connect use a confidential client with the code flow (the recommended way), with PKCE (recommended). Public OpenID Connect/OAuth clients aren't recommended for web apps. For a web app with no independent backend, use the Backend for Frontend (BFF) pattern (recommended). With a Microsoft identity provider, use the Microsoft.Identity.Web packages (recommended). Don't deploy an app with IdentityModelEventSource.ShowPII to productive servers.
- [ASP-023](../standards/aspnetcore.md) (proposed): Protect the Data Protection key ring with appropriate permissions, limit access to its storage to the app itself, and specify an explicit key encryption mechanism for production deployments (recommended). Configure the data protection stack to work in a server farm. Pass a unique purposes parameter to CreateProtector.
- [ASP-024](../standards/aspnetcore.md) (proposed): Register a delegating handler for an HttpClient in DI as a transient service, never singleton or scoped.
- [CRF-013](../standards/craft.md) (accepted): Wherever the tests run the app, the container validates scopes and its registrations (ValidateScopes, ValidateOnBuild) in every environment they use, not only in Development, so a singleton that captures a scoped service, and a scoped service resolved from the root, fail a test; the app's own setting is left as it is. CRF-020 holds Microsoft's dependency injection guidelines.
- [DAT-002](../standards/data.md) (proposed): An app with a server relational database reaches it through EF Core, and its schema changes only through EF Core code-first migrations kept in the repo, never EnsureCreated (tests apply the migrations too, DAT-005); a test fails when the model has changes no migration covers.
- [DAT-005](../standards/data.md) (proposed): Integration and functional tests of an app with a server database, and its local development, run against the production database engine, in a container (Testcontainers for tests) or its official emulator (the Azure Cosmos DB emulator), with the app's migrations applied; never the EF Core in-memory provider, and never SQLite standing in for another engine.
- [DAT-013](../standards/data.md) (proposed): Use expand -> migrate -> contract schema changes to keep old and new app versions compatible during a transition.
- [DAT-014](../standards/data.md) (proposed): For automated deployment of EF Core migrations, use a migration bundle; use a SQL script instead when the SQL must be reviewed, modified, archived, or handed to a DBA before it is applied. Applying migrations at runtime needs careful consideration in production, and a bundle is preferred for automation and a SQL script where review and approval are required; don't make every application replica run migrations from its entrypoint. Use a separate identity for deployment that has permission to change the schema, so the identity the application uses at run time should normally have only the permissions to read and write data, and don't store production connection strings in source control or embed them in the bundle.
- [NET-002](../standards/dotnet.md) (proposed): When adding resilience to an HTTP client, add only one resilience handler and avoid stacking handlers; to combine several strategies, consider the AddResilienceHandler extension method.
- [HST-001](../standards/hosting.md) (proposed): Don't auto-activate services with a scoped or transient lifetime, and keep what an auto-activated service does at startup fast. For longer-running initialization, consider background services or hosted services.
- [HST-002](../standards/hosting.md) (proposed): Don't cache an HttpClient that IHttpClientFactory created for a long time, and don't inject a typed client into a singleton service: request a client in a timely manner or each time you need one. Don't cache scope-related information (such as data from HttpContext) inside HttpMessageHandler instances or their dependencies. Don't register a typed client separately, because AddHttpClient already registers it. Don't start a large number of HTTP/1.1 requests at once without specifying limits.
- [HST-003](../standards/hosting.md) (proposed): Name a log category after the fully qualified class that writes the message (an ILogger<T> does it), and use log message template formatting, not string interpolation. If a logging data store is slow, don't write to it directly from a logger.
- [HST-004](../standards/hosting.md) (proposed): Use AddDistributedMemoryCache only in development or testing; it isn't a viable production implementation of IDistributedCache.
- [OPS-001](../standards/operations.md) (accepted): Every ASP.NET Core app sends its logs, metrics and traces through OpenTelemetry, set up in one ServiceDefaults project, and exports them over OTLP when OTEL_EXPORTER_OTLP_ENDPOINT is set.
- [OPS-002](../standards/operations.md) (accepted): Every ASP.NET Core app maps /health (readiness: every check, its database included) and /alive (liveness: only checks tagged live) in every environment, answering with the status word only; a Healthy answer is cached briefly, and a slow check is cut off with a 504.
- [OPS-003](../standards/operations.md) (accepted): Every HttpClient comes from IHttpClientFactory and gets the standard resilience handler (timeouts, retries with backoff, circuit breaker) from the ServiceDefaults project, retrying only safe methods; a client that needs other settings removes the default handler (RemoveAllResilienceHandlers, experimental: suppress EXTEXP0001 with a reason) before adding its own. An app that needs cookies, which the factory's pooled handlers would share, keeps a long-lived HttpClient for each cookie container instead, over a SocketsHttpHandler with a PooledConnectionLifetime and wrapped in a ResilienceHandler, as the HttpClient guidelines page shows, decided by an ADR that also lifts the constructor ban there (CRF-010).
- [OPS-005](../standards/operations.md) (accepted): An app shuts down gracefully: on SIGTERM its host stops taking requests and gives in-flight work a shutdown timeout that ends before the platform's grace period (25 seconds where the platform allows 30, Kubernetes' default), and long-running work stops on the host's stopping token or the request's cancellation token, which every call passes on.
- [OPS-006](../standards/operations.md) (accepted): An app's settings are options validated when it starts (ValidateDataAnnotations or a validator, and ValidateOnStart), so bad configuration stops it at startup instead of failing requests later.
- [OPS-007](../standards/operations.md) (accepted): An ASP.NET Core app follows Microsoft's ASP.NET Core best practices: avoid blocking calls; make hot code paths asynchronous and call data access, I/O and long-running operations asynchronously where an asynchronous API exists; avoid reading large request bodies or response bodies into memory; never create and dispose HttpClient instances directly, and use HttpClientFactory to retrieve them (OPS-008 names the lifetime options); do not use HttpContext after the request is complete, and do not access it from multiple threads. For high-performance logging, use LoggerMessageAttribute with compile-time source generation.
- [OPS-009](../standards/operations.md) (accepted): An app with long-running operations that need to finish gracefully should subscribe to the host's ApplicationStopping event, which the host signals when it receives a shutdown signal such as SIGTERM.
- [OPS-010](../standards/operations.md) (accepted): Use a liveness probe to describe the liveness of the process, running no other checks, and a readiness probe to report "not ready" until the app has finished its startup work; separate readiness and liveness checks are useful under an orchestrator such as Kubernetes.
- [OPS-013](../standards/operations.md) (proposed): Configure data protection to create a persistent cryptographic key store, even if user code never calls the Data Protection APIs, because ASP.NET Core's authentication and anti-forgery middleware use it.
- [OPS-016](../standards/operations.md) (proposed): When a systemd unit runs a .NET app, avoid setting KillSignal=SIGINT: .NET lifetime integrations listen for SIGTERM to start a graceful shutdown.
- [OPS-017](../standards/operations.md) (proposed): If the /health and /alive endpoints are enabled outside Development, it's recommended to protect them with routing features such as host filtering or authorization.
- [SEC-007](../standards/security.md) (proposed): Every ASP.NET Core app sets a fallback authorization policy that requires a signed-in user, so an endpoint needs one unless it opts out with AllowAnonymous; only endpoints that must be public opt out (health probes, the Development OpenAPI document), each with a comment saying why, and a test pins that list.
- [SEC-008](../standards/security.md) (proposed): An app never stores passwords or issues its own access tokens: users sign in with an OpenID Connect provider (Microsoft Entra ID or Entra External ID unless an ADR picks another), and an HTTP API accepts its access tokens with AddJwtBearer, which checks their signature, issuer, audience and lifetime, set under Authentication:Schemes:Bearer; development uses dotnet user-jwts, whose key stays in user secrets; ASP.NET Core Identity or any other scheme needs an ADR.
- [SEC-009](../standards/security.md) (proposed): Every read or change of a user's data is limited to that user's data in the query itself, in the application and data layers, not only in the endpoint; the user's id is the token's sub claim, which the fallback policy requires (unique within one issuer, so an app that trusts more than one keys on the issuer and sub together), and another user's item answers 404, as one that doesn't exist does.
- [SEC-010](../standards/security.md) (proposed): Every value a client sends is checked where it enters the app against what's allowed: required fields, a maximum length for every string, URI and collection, and a range for every number. A value outside those bounds gets a 400 validation problem that names the field; a domain rule's refusal is a 400 Problem (API-006); neither repeats the value. API-006 says how a Minimal API does it.
- [SEC-011](../standards/security.md) (accepted): Every ASP.NET Core app applies Microsoft's Kestrel production security checklist for where it's hosted, at the edge or behind a proxy: HTTPS only (at the edge, Kestrel terminates TLS 1.2 or later and serves no plain HTTP; behind a proxy, the proxy does), host filtering with its own AllowedHosts, HSTS outside Development, a rate limit for each caller, CORS only for named origins, a request body cap well under the 30 MB default, and no Server header; behind a proxy, forwarded headers only from KnownProxies or KnownIPNetworks, and never through ASPNETCORE_FORWARDEDHEADERS_ENABLED.
- [SEC-017](../standards/security.md) (proposed): For a server-side app where most or all endpoints require authentication, set a fallback authorization policy that requires an authenticated user; it is secure by default and protects newly added endpoints. Apply AllowAnonymous to an endpoint that is intentionally public. ASVS 8.2.1: function-level access is restricted to consumers with explicit permissions.
- [SEC-020](../standards/security.md) (proposed): Define and enforce a maximum size of data on all incoming parameters and payloads, such as maximum length for strings, maximum number of elements in arrays and maximum upload file size. Add server-side validation for query string and request body parameters, especially the one that controls the number of records returned. ASVS 2.2.1 and 2.2.2: validate input against an allow list or expected structure and limits, at a trusted service layer.
- [SEC-021](../standards/security.md) (accepted): Apply Microsoft's Kestrel security checklist for where the app is hosted. At the edge: use host-filtering middleware, enable HTTPS redirection, handle rate limiting in the application, don't enable the Forwarded Headers middleware, verify ASPNETCORE_FORWARDEDHEADERS_ENABLED isn't set, consider lowering the request body limit significantly for an API that accepts no large uploads, and consider disabling the Server header. Behind a reverse proxy: the Forwarded Headers middleware is required, with KnownProxies or KnownIPNetworks configured explicitly. OWASP API4: limit how often a client can interact with the API within a defined timeframe (rate limiting).
- [SEC-022](../standards/security.md) (accepted): Most applications should strive for OWASP ASVS Level 2; Level 1 is the minimum starting point for securing an application.
- [UI-001](../standards/ui.md) (proposed): Every UI an app ships meets WCAG 2.2 level AA: web UI (Blazor, Razor) as written, native UI (MAUI, desktop) as W3C's WCAG2ICT note applies it. Building UI, an agent checks at least the success criteria UI-003 lists, keeping each one's own exceptions, such as a link inside a sentence or a data table that needs two dimensions.
- [UI-002](../standards/ui.md) (proposed): Every page of a web UI (Blazor, Razor) has a Playwright test in the app's E2E.Tests project that opens it, checks it loaded, and runs axe's WCAG 2.2 level A and AA rules (the tags wcag2a, wcag2aa, wcag21a, wcag21aa and wcag22aa), failing on any violation; what a person does that axe can't see, such as where focus goes after a link or the first Tab, gets its own Playwright test.
- [UI-003](../standards/ui.md) (proposed): To meet WCAG 2.2 level AA, a UI must meet, among all the other level A and AA success criteria: a text alternative for non-text content, and a name for every control (1.1.1); structure and relationships that can be programmatically determined (1.3.1); color not as the only visual means of conveying information (1.4.1); a contrast ratio of at least 4.5:1 for text, 3:1 for large text (1.4.3); text resizable to 200 percent without loss of content or functionality (1.4.4); content that reflows at a width equivalent to 320 CSS pixels (1.4.10); a contrast ratio of at least 3:1 for the visual information that identifies user interface components and states (1.4.11); all functionality operable through a keyboard interface (2.1.1) with no keyboard trap (2.1.2); a focus order that preserves meaning and operability (2.4.3); a visible keyboard focus indicator (2.4.7) that isn't entirely hidden by author-created content (2.4.11); pointer targets at least 24 by 24 CSS pixels unless an exception applies (2.5.8); labels or instructions where content requires input (3.3.2); no cognitive function test in authentication unless an alternative or a mechanism is offered (3.3.8); and a programmatically determinable name and role for every user interface component (4.1.2). For native UI, W3C's WCAG2ICT note says how each criterion applies.

## Consequences

- A Razor Pages or MVC app gets the common ruleset, the shared web rules and the view and page rules.
- ASP-010, ASP-011 and ASP-013 are proposed, like every rule from the 2026-11-17 pages.
- **Gap:** Tag helper authoring and view components have no rule: the pages state naming and layout conventions, not recommendations. The localization pages have no guidance either.

## Pillars affected

- **Security:** CSRF, overposting and Raw output rules (ASP-005, ASP-011, ASP-013).
- **Reliability:** session and cache rules say never to depend on them (ASP-004, ASP-008).
- **Operational Excellence:** shared logging and configuration rules (ASP-002, ASP-003).
