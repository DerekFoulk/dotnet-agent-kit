# ADR-0049: Every assembly declares it isn't CLS-compliant, and CA1014 is on

- **Status:** Accepted
- **Date:** 2026-11-11

## Context

STY-003 says every analyzer rule is on, and an opt-out needs an ADR. ADR-0043 turned on the rules `AnalysisLevel latest-all` leaves off, all but one: CA1014, "Mark assemblies with CLSCompliantAttribute". It waited for this decision (GAP-021).

The Common Language Specification (CLS) is the set of features every .NET language must support: no unsigned integers in a public signature, no public names that differ only in case, no public name starting with `_`, and so on. An assembly that declares `[assembly: CLSCompliant(true)]` makes the compiler check that its public surface keeps to it (warnings CS3001 to CS3027), so code in any .NET language can call it.

What Microsoft says:

- **CA1014's page:** "Good design dictates that all assemblies explicitly indicate CLS compliance." Under "When to suppress warnings": "Do not suppress a warning from this rule. If you do not want the assembly to be compliant, apply the attribute and set its value to `false`."
- **Language independence:** "If you are developing an app rather than a library (that is, if you aren't exposing types or members that can be consumed by other app developers), the CLS compliance of the program elements that your app consumes are of interest only if your language does not support them."
- **`CLSCompliantAttribute`'s remarks:** "CLS compliance is primarily of concern to library developers who want to ensure that their libraries are accessible in any language that targets .NET."
- **The code analysis overview** lists CA1014 among the rules `latest-all` leaves off that "might be deprecated in a future version".

What measurement showed (SDK 10.0.404, the sample with `[assembly: CLSCompliant(true)]` on every project, warnings not treated as errors): 32 distinct places, in three groups. (GAP-021's 48 counted the build's output lines, which repeat some.)

- **18 × CS3016, arrays as attribute arguments:** xUnit's `[InlineData(0, 101)]`, whose constructor takes `params object[]`.
- **9 × CS3001, CS3002, CS3003 and CS3009, a public signature using a type that isn't CLS-compliant:** `DbContext`, `ModelBuilder` and `DbContextOptions<T>` in `BookmarksDbContext`; `WebApplication` in `MapDefaultEndpoints`; xUnit's and ArchUnitNET's types in three test classes. ASP.NET Core, EF Core and the test libraries don't declare CLS compliance, so any public type built on them breaks it.
- **5 × CS3008, an identifier starting with `_`:** in `XunitAutoGeneratedEntryPoint.cs`, which xUnit generates in each test project.

The kit's apps are apps: a web API and the class libraries that serve it, with types kept internal where CA1515 asks. No other language consumes them.

## Options

### Option 1: Declare every assembly not CLS-compliant, and turn CA1014 on

`Directory.Build.props` adds `[assembly: CLSCompliant(false)]` to every assembly through an `AssemblyAttribute` item, as it already does for CA1017's `ComVisible(false)`; `.globalconfig` turns CA1014 on.

- **Trade-offs:** follows Microsoft's CA1014 page to the letter: the rule is on, nothing is suppressed, and every assembly states its position. It costs no code change, because an app makes no claim it would have to keep. A library meant for other .NET languages opts in instead: it removes the item and declares `CLSCompliant(true)`, and the compiler checks it. STY-003 then holds with no exception.
- **Reversibility:** easy. One item in `Directory.Build.props` and one line in `.globalconfig`.
- **Risk:** low. A project that already declares the attribute itself gets CS0579 (duplicate attribute) and removes the kit's item, as `Directory.Build.props` explains. If Microsoft deprecates CA1014, the line in `.globalconfig` goes.

### Option 2: Declare every assembly CLS-compliant, and fix what breaks

- **Trade-offs:** the strongest promise, and the compiler checks it. But the promise is one nobody asks an app to keep. Every public type that touches ASP.NET Core or EF Core needs `[CLSCompliant(false)]`, since those frameworks don't declare compliance; so does every theory with `[InlineData]`. xUnit's generated entry point can't be marked at all, so each test project would need its own `CLSCompliant(false)` anyway. That's 32 places in the sample, more in every app, with no reader in another language to benefit. Microsoft's guidance puts CLS compliance on library developers.
- **Reversibility:** moderate: the attributes spread through the code.
- **Risk:** medium. Each framework update or new test can break the build over a rule that protects no one.

### Option 3: Leave CA1014 off, with this ADR as the recorded opt-out

- **Trade-offs:** no change at all. But STY-003 keeps an exception, and CA1014's own page says not to suppress it: applying the attribute with `false` is how Microsoft says to say "not compliant".
- **Reversibility:** easy.
- **Risk:** low, but an assembly states nothing about CLS compliance, which is what the rule exists to stop.

## Recommendation

Option 1: it's what Microsoft's CA1014 page says to do for an assembly that isn't meant to be CLS-compliant, it keeps every rule on, and it changes no code.

## Decision

Option 1, decided in auto mode (ADR-0035) on 2026-11-11, within STY-003 and the owner's request of 2026-11-11 to close the open scorecard gaps.

## Consequences

- `Directory.Build.props` adds `[assembly: CLSCompliant(false)]` to every assembly; every new app gets it, since the file is a kit copy (ADR-0032), and the sync job carries it to existing apps.
- `.globalconfig` turns CA1014 on, so it now turns on every rule `latest-all` leaves off. `tools/tests/BuildConfig.Tests.ps1` builds a fixture, `NoClsCompliant`, that removes the declaration and must fail with CA1014.
- STY-003's enforcement and `docs/standards/craft.md` no longer name an exception; GAP-021 is closed.
- A library an app publishes for other .NET languages removes the kit's item and declares `[assembly: CLSCompliant(true)]`, then marks each non-compliant public member `[CLSCompliant(false)]` with a compliant alternative, as Microsoft's language independence page describes.

## Pillars affected

- **Operational excellence:** every rule stays on, with no exception to explain or track.
- **Reliability, security, cost, performance:** none. The attribute is metadata.
