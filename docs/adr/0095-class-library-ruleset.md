# ADR-0095: Class library ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A class library is a project that other apps or libraries reference, usually as a NuGet package. Its `project-types.yml` entry is `class-library` (Class library), and its docs start at <https://learn.microsoft.com/dotnet/standard/library-guidance/>.

ADR-0082 makes every rule name the project types it applies to. ADR-0084 gives an app only the common ruleset plus the rulesets of its project types. This ADR records the ruleset for `class-library` (Class library), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/dotnet.md`):

- <https://learn.microsoft.com/dotnet/standard/library-guidance/dependencies-net>: choose a dependency policy; remove out-of-support target frameworks (CS-034).
- <https://learn.microsoft.com/dotnet/standard/library-guidance/nuget-package-compatibility-rules>: same or greater API surface across frameworks (CS-035).
- <https://learn.microsoft.com/dotnet/standard/net-standard>: target .NET Standard 2.0 unless an earlier version is needed (CS-036).
- <https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/extension-methods>: no extension methods to dodge a version increment (CS-016).
- <https://learn.microsoft.com/dotnet/standard/asynchronous-programming-patterns/async-wrappers-for-synchronous-methods>: no offload-only async methods or sync wrappers (CS-021).
- <https://learn.microsoft.com/dotnet/core/extensions/options-library-authors>: registration extension methods and namespaces (HST-005).

CS-016, CS-021, CS-034, CS-035, CS-036 and HST-005 name `class-library` alone. A library gets the common rules too, which carry most C# and supply-chain guidance, and none of the app rules for web, UI or databases.

## Options

### Option 1: A ruleset for Class library

- **Trade-offs:** An app of this type gets the common rules plus the rules that name `class-library`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `projectTypes` list per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `projectTypes` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a desktop app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `class-library` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the project-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

## The ruleset

Generated by Build-AgentRules.ps1 from docs/standards; proposed rules are marked, and aren't in force until the owner accepts them.

<!-- ruleset: class-library -->
- [CS-016](../standards/csharp.md) (proposed): In a class library you own, don't use extension methods to avoid incrementing the assembly version; follow the .NET guidelines for assembly versioning.
- [CS-021](../standards/csharp.md) (proposed): A library doesn't expose an asynchronous method purely for offloading, and doesn't expose a synchronous method that wraps an asynchronous implementation; the consumer decides whether to offload or to block.
- [CS-034](../standards/csharp.md) (proposed): A library's author chooses a dependency policy deliberately, removes out-of-support target frameworks from the package, doesn't reference a package when the framework provides the API, and avoids using branching to drop support for in-support frameworks.
- [CS-035](../standards/csharp.md) (proposed): A package's assemblies for compatible frameworks must expose the same (or a superset of) API surface; never decrease the assembly version across releases, and change it with each release (unless the package overlaps with a .NET shared framework); avoid binary breaking changes to the public API and avoid removing package dependencies between compatible versions; and consider enabling Package Validation with a baseline version.
- [CS-036](../standards/csharp.md) (proposed): A library that targets .NET Standard should target .NET Standard 2.0 unless it needs to support an earlier version, shouldn't target .NET Standard 1.x, and, where .NET Framework isn't needed, should skip .NET Standard 2.1 and target the current .NET.
- [HST-005](../standards/hosting.md) (proposed): A library that adds registration extension methods must not use the Microsoft.Extensions.DependencyInjection namespace unless it is an official Microsoft package, and must not use names that are already part of the .NET ecosystem from official Microsoft packages.
<!-- end ruleset -->

## Consequences

- A class library gets the common ruleset and the six rules above.
- The six rules are proposed.
- Rules about publishing (SourceLink, versioning, strong naming) wait for a pass over the pages named in the gap below.
- **Gap:** Eight library-guidance pages were marked "audited, not re-read" and have no rule: breaking-changes, cross-platform-targeting, dependencies, nuget, publish-nuget-package, sourcelink, strong-naming and versioning. They carry DO and AVOID lists like the dependencies-net page does. No existing rule cites them, so a follow-up pass should add a rule for each page or confirm the earlier audit's verdict.

## Pillars affected

- **Reliability:** compatibility and target-framework rules keep consumers working (CS-035, CS-036).
- **Operational Excellence:** dependency policy (CS-034).
- **Security:** not affected beyond the common supply-chain rules.
