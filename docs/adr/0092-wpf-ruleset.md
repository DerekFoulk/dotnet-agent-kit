# ADR-0092: WPF ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A WPF app is a Windows desktop app built on XAML and .NET. Its `project-types.yml` entry is `wpf` (WPF), and its docs start at <https://learn.microsoft.com/dotnet/desktop/wpf/overview/>. WPF serves Windows alone and is the older stack, so ARC-014 asks a new WPF app for an ADR saying why.

ADR-0082 makes every rule name the project types it applies to. ADR-0084 gives an app only the common ruleset plus the rulesets of its project types. This ADR records the ruleset for `wpf` (WPF), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/desktop.md`):

- <https://learn.microsoft.com/dotnet/desktop/wpf/advanced/application-startup-time>: minimize external resources at startup (WPF-001).
- <https://learn.microsoft.com/dotnet/desktop/wpf/advanced/freezable-objects-overview>: freeze Freezables you will not modify (WPF-002).
- <https://learn.microsoft.com/dotnet/desktop/wpf/advanced/optimizing-performance-other-recommendations>: avoid ScrollBarVisibility Auto (WPF-003).
- <https://learn.microsoft.com/dotnet/desktop/wpf/advanced/use-automatic-layout-overview>: XAML, no absolute positions, localization (WPF-004).
- <https://learn.microsoft.com/dotnet/desktop/wpf/properties/custom-dependency-properties>: wrappers only GetValue and SetValue (WPF-005).
- <https://learn.microsoft.com/dotnet/desktop/wpf/controls/guidelines-for-designing-stylable-controls>: do not enforce template contracts (WPF-006).
- <https://learn.microsoft.com/dotnet/desktop/xaml-services/security-considerations>: untrusted XAML is untrusted code (WPF-007).
- <https://learn.microsoft.com/windows/apps/get-started/best-practices>: no admin rights; installer behavior; signing (WUI-018, WUI-019, WUI-021).

WPF-001 to WPF-007 name `wpf` alone. WUI-018, WUI-019 and WUI-021, which come from Windows app pages, also name it, as do the desktop architecture and accessibility rules (ARC-010, ARC-011, ARC-014, UI-001, UI-003).

## Options

### Option 1: A ruleset for WPF

- **Trade-offs:** An app of this type gets the common rules plus the rules that name `wpf`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `projectTypes` list per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `projectTypes` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a desktop app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `wpf` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the project-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

## The ruleset

Generated by Build-AgentRules.ps1 from docs/standards; proposed rules are marked, and aren't in force until the owner accepts them.

- [ARC-010](../standards/architecture.md) (proposed): In MAUI and desktop apps, view models and all other logic live in UI-independent libraries (ARC-003); a UI project, one that sets UseMaui, UseWPF, UseWindowsForms or UseWinUI, holds only views, platform code and startup wiring, no other project references it, and the coverage gate exempts it.
- [ARC-011](../standards/architecture.md) (proposed): A new general-purpose Windows desktop app is recommended to use WinUI 3, the native UI framework delivered with the Windows App SDK; a team expecting to target several platforms should start with .NET MAUI (Microsoft names React Native for Desktop beside it), which uses WinUI 3 when running on Windows.
- [ARC-014](../standards/architecture.md) (proposed): A new desktop app uses the framework ARC-011 names for its platforms (WinUI 3 for a Windows desktop app, .NET MAUI for several platforms); a new WPF or Windows Forms app needs an ADR that says why.
- [UI-001](../standards/ui.md) (proposed): Every UI an app ships meets WCAG 2.2 level AA: web UI (Blazor, Razor) as written, native UI (MAUI, desktop) as W3C's WCAG2ICT note applies it. Building UI, an agent checks at least the success criteria UI-003 lists, keeping each one's own exceptions, such as a link inside a sentence or a data table that needs two dimensions.
- [UI-003](../standards/ui.md) (proposed): To meet WCAG 2.2 level AA, a UI must meet, among all the other level A and AA success criteria: a text alternative for non-text content, and a name for every control (1.1.1); structure and relationships that can be programmatically determined (1.3.1); color not as the only visual means of conveying information (1.4.1); a contrast ratio of at least 4.5:1 for text, 3:1 for large text (1.4.3); text resizable to 200 percent without loss of content or functionality (1.4.4); content that reflows at a width equivalent to 320 CSS pixels (1.4.10); a contrast ratio of at least 3:1 for the visual information that identifies user interface components and states (1.4.11); all functionality operable through a keyboard interface (2.1.1) with no keyboard trap (2.1.2); a focus order that preserves meaning and operability (2.4.3); a visible keyboard focus indicator (2.4.7) that isn't entirely hidden by author-created content (2.4.11); pointer targets at least 24 by 24 CSS pixels unless an exception applies (2.5.8); labels or instructions where content requires input (3.3.2); no cognitive function test in authentication unless an alternative or a mechanism is offered (3.3.8); and a programmatically determinable name and role for every user interface component (4.1.2). For native UI, W3C's WCAG2ICT note says how each criterion applies.
- [WUI-018](../standards/winui.md) (proposed): A Windows desktop app must not require administrative privileges to install or run; where a feature needs them, consider a separate process for it. Use your language or framework's standard libraries for cryptography, never your own, and always use secured connections such as TLS when transmitting data. Always get the user's consent before collecting and storing personal data.
- [WUI-019](../standards/winui.md) (proposed): An installer for a Windows desktop app shouldn't leave temporary files behind, and should avoid requiring elevated permissions or operating system reboots where possible. Consider MSIX for a seamless install, update and uninstall, and consider letting users preserve their data when they uninstall.
- [WUI-021](../standards/winui.md) (proposed): Sign all the files of a Windows app distributed outside the Microsoft Store with a valid certificate; unsigned files build SmartScreen reputation anew with every update. Azure Artifact Signing is Microsoft's recommended code signing service for that case.
- [WPF-001](../standards/wpf.md) (proposed): Reduce a WPF app's startup time: in general, minimize the use of external resources such as network, web services or disk, and consider postponing initialization code until after the main application window is rendered.
- [WPF-002](../standards/wpf.md) (proposed): Freeze a Freezable, such as a brush, when its conditions allow and you don't intend to modify it, to gain the performance benefits. Check CanFreeze before freezing, and IsFrozen to see whether it already is.
- [WPF-003](../standards/wpf.md) (proposed): In WPF, whenever possible avoid the Auto value for HorizontalScrollBarVisibility and VerticalScrollBarVisibility. Use automatic hyphenation and the optimal paragraph feature only when needed: it is recommended that you don't use either unless you need it.
- [WPF-004](../standards/wpf.md) (proposed): Design a WPF UI for localization. Write it in XAML and avoid creating UI in code. Avoid absolute positions and fixed sizes, and use relative or automatic sizing instead: use SizeToContent and keep widths and heights set to Auto, and use Grid and its size-sharing feature. Avoid using Canvas to lay out UIs. Avoid fixed dimensions for panels and controls, to prevent clipping localized text that may be longer than the source text.
- [WPF-005](../standards/wpf.md) (proposed): In a WPF custom control, implement a property as a dependency property when it should support WPF's property features, and keep the CLR wrapper to GetValue and SetValue code except in rare cases, because WPF and XAML bypass the wrapper. Avoid setting a dependency property value in the constructor of a class that might be used as a base class; consider setting a default value in property metadata instead.
- [WPF-006](../standards/wpf.md) (proposed): Make a WPF custom control resilient to its template: don't strictly enforce template contracts, and don't throw an exception when any aspect of a template contract isn't followed. Provide a control contract that says which parts and states the ControlTemplate should define, and define the control's visual structure and behavior in the template instead of in code.
- [WPF-007](../standards/wpf.md) (proposed): Treat untrusted XAML generally the same as untrusted code, and use sandboxing or other metaphors to keep it from accessing trusted code. Don't share XAML reader instances, a nondefault XAML schema context, or settings for XAML reader and writer classes between trusted and untrusted code.

## Consequences

- A WPF app gets the common ruleset, WPF-001 to WPF-007 and the Windows desktop rules above, and an ADR is required for choosing WPF (ARC-014).
- WPF-001 to WPF-007 are proposed.
- **Gap:** The startup page's NGen, ClickOnce and Authenticode advice is .NET Framework only and was not ruled. The inventory marks the dialog boxes page (a DO and DON'T list) out of scope as UX design; the lead may reverse that.

## Pillars affected

- **Performance Efficiency:** startup, freezing and scrolling rules (WPF-001 to WPF-003).
- **Security:** untrusted XAML, no admin rights, signing (WPF-007, WUI-018, WUI-021).
- **Operational Excellence:** custom control rules keep controls maintainable (WPF-005, WPF-006).
