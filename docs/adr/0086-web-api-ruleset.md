# ADR-0086: ASP.NET Core Web API ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A Web API is an ASP.NET Core app that serves HTTP, gRPC or SignalR endpoints with no UI of its own. Its `app-types.yml` entry is `web-api` (ASP.NET Core Web API), and its docs start at <https://learn.microsoft.com/aspnet/core/fundamentals/apis>.

ADR-0084 makes every rule name its `scope`, `core` or the app types it applies to, and gives an app only the core ruleset (ADR-0085) plus the rulesets of its app types. This ADR records the ruleset for `web-api` (ASP.NET Core Web API), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/aspnetcore.md`):

- <https://learn.microsoft.com/aspnet/core/fundamentals/apis>: Minimal APIs for a new HTTP API; controllers where the app needs them (API-001, API-008).
- <https://learn.microsoft.com/aspnet/core/web-api/>: controller-based APIs derive from ControllerBase (ASP-012).
- <https://learn.microsoft.com/aspnet/core/fundamentals/error-handling>: Problem Details; exception handler in production (API-002, API-010).
- <https://learn.microsoft.com/aspnet/core/fundamentals/best-practices>: avoid blocking calls, large bodies and HttpContext misuse (OPS-007).
- <https://learn.microsoft.com/aspnet/core/fundamentals/dependency-injection>: no service locator or static state (ASP-001).
- <https://learn.microsoft.com/aspnet/core/security/app-secrets>: no secrets in configuration files (ASP-002).
- <https://learn.microsoft.com/aspnet/core/security/anti-request-forgery>: no state change on GET; antiforgery for cookie apps (ASP-005).
- <https://learn.microsoft.com/aspnet/core/mvc/models/model-binding>: overposting: view models over [Bind] (ASP-011).
- <https://learn.microsoft.com/aspnet/core/performance/caching/response>: response caching only for user-independent content (ASP-009).
- <https://learn.microsoft.com/aspnet/core/grpc/client>: gRPC: reuse channels, dispose streams, set deadlines; TLS only (ASP-017, ASP-018).
- <https://learn.microsoft.com/aspnet/core/signalr/hubs>: SignalR: no hub state, sticky sessions, named CORS origins (ASP-019, ASP-020).
- <https://learn.microsoft.com/aspnet/core/security/authentication/configure-jwt-bearer-authentication>: no self-issued tokens in production (SEC-008, SEC-018).
- <https://learn.microsoft.com/aspnet/core/fundamentals/servers/kestrel/security-considerations>: Kestrel production checklist (SEC-011, SEC-021).
- <https://learn.microsoft.com/aspnet/core/fundamentals/http-requests>: delegating handlers are transient; resilience (ASP-024, OPS-003).

Web APIs are the type the kit's first rules were written for, so most of its API, security and operations rules name `web-api` together with `blazor`. The rest name `web-api` alone, among them API-006, ASP-012, ASP-017, ASP-018 and SEC-013; the block below lists them all. Razor Pages and MVC apps, and workers and console apps, aren't supported app types yet (ADR-0084), so no rule names them.

## Options

### Option 1: A ruleset for ASP.NET Core Web API

- **Trade-offs:** An app of this type gets the core rules plus the rules whose scope names `web-api`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `scope` per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `scope` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a .NET MAUI app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `web-api` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the app-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

- [API-001](../standards/api-design.md) (should): An app's API style is chosen in its plan: an HTTP API with Minimal APIs by default; gRPC, SignalR, controllers or GraphQL only where a Microsoft page recommends that style for the app's scenario (API-008) or the owner asks for it by name, and the plan says which.
- [API-008](../standards/api-design.md) (should): For new ASP.NET Core API projects, Minimal APIs are recommended; consider controller-based APIs if you need model binding extensibility, form binding support (including IFormFile), advanced validation features, application parts or the application model, or OData support. gRPC is well suited to microservices, point-to-point real-time communication, polyglot environments, network-constrained environments and inter-process communication; other frameworks are recommended over gRPC for browser-accessible APIs and for broadcast real-time communication, and SignalR is a useful framework for broadcasting.
- [API-002](../standards/api-design.md) (must): Every HTTP API error response is Problem Details (RFC 9457): AddProblemDetails, UseExceptionHandler and UseStatusCodePages; a client error such as malformed input stays a 400 in every environment, and outside Development a 500 never carries the exception's message or stack.
- [API-003](../standards/api-design.md) (must): An HTTP API describes itself with the built-in OpenAPI document (Microsoft.AspNetCore.OpenApi) and typed results; the document, and any UI for it such as Scalar or Swagger UI, is mapped in Development only; a contract test snapshots the document, so every change to the API shows in review.
- [API-004](../standards/api-design.md) (must): Every HTTP endpoint that lists a collection pages it in the data store, in a deterministic order, with limit (default 25, at most 100) and offset (at most 10,000) query parameters, and answers an object with the page's items and a nextLink to the next page, null on the last page or the last one the offset cap allows.
- [API-005](../standards/api-design.md) (should): An HTTP API isn't versioned until its first breaking change to a contract that another app or a released client depends on; that change gets an ADR that picks how versions are told apart (URI, query string or header) and the package, a new version, and the earlier version stays until its callers move.
- [API-006](../standards/api-design.md) (should): A Minimal API validates its inputs with the built-in validation (AddValidation and DataAnnotations attributes on parameters and request types), so invalid input gets a 400 validation problem before the handler runs; a domain rule (such as a bookmark's URL being http or https) stays in the domain, and the endpoint turns its exception into a 400 Problem.
- [API-007](../standards/api-design.md) (must): In an HTTP API, when possible, base resource URIs on nouns and not verbs, and avoid using verbs in URIs to represent operations; a POST that creates a resource synchronously should return 201 Created and identify the resource in the Location header; GET, HEAD, PUT and DELETE must be idempotent; and for work that takes time, consider making the method asynchronous: an asynchronous method should return 202 Accepted, include the status endpoint's URI in the 202's Location header, and if the operation creates a new resource, the status endpoint should return 303 See Other after it completes, with a Location header that gives the new resource's URI.
- [API-009](../standards/api-design.md) (should): OpenAPI user interfaces (Swagger UI, ReDoc, Scalar) should only be enabled in development environments.
- [API-010](../standards/api-design.md) (must): In non-development environments, use the exception handler middleware to produce an error payload. Don't enable the Developer Exception Page unless the app is running in the Development environment, and don't share detailed exception information publicly when the app runs in production.
- [API-011](../standards/api-design.md) (should): For an endpoint that returns a collection, use limit and offset query parameters with meaningful defaults, such as limit=25 and offset=0, and consider an upper limit on the number of items returned. Apply pagination in the data store, not after loading the entire collection, with a deterministic sort order; include a next-page link or continuation token in the response, omitted or null on the last page; and for a large or frequently changing collection, evaluate cursor-based pagination.
- [API-012](../standards/api-design.md) (should): Support versioning in the API contract: when you introduce a breaking API change, introduce a new API version, continue to support the previous version, and let clients select which version to call. Make API changes backward compatible when possible.
- [API-013](../standards/api-design.md) (must): An HTTP API's URIs name a collection with a plural noun, and use a verb sparingly, only for an operation that isn't a resource.
- [ARC-001](../standards/architecture.md) (must): Web apps use Clean Architecture in one deployable app; each distinct business area is a module with Domain, Application, Infrastructure, Presentation and Contracts projects, and Application code is grouped by feature; a project can deviate by ADR.
- [ARC-002](../standards/architecture.md) (must): Modules talk to each other only through their Contracts projects; a module never reads or writes another module's tables, and an app never shares its database with another app.
- [ARC-016](../standards/architecture.md) (should): ASP.NET Core's built-in use of and support for dependency injection makes Clean Architecture the most appropriate way to structure non-trivial monolithic applications. In it, the Application Core holds the business model, including the interfaces for operations performed using Infrastructure; Infrastructure's services should implement interfaces defined in the Application Core; and the UI project should reference the Application Core project, and its types should interact with infrastructure strictly through interfaces defined in Application Core.
- [ASP-001](../standards/aspnetcore.md) (should): Prefer requesting dependencies as constructor parameters over resolving services from RequestServices. Services resolved from the container should never be disposed by the developer. CRF-020 carries the rest of Microsoft's dependency injection guidance (the service locator pattern, stateful static classes and members, direct instantiation of dependent classes).
- [ASP-002](../standards/aspnetcore.md) (must): Never store passwords or other sensitive data in configuration provider code or in plain text configuration files, and don't use production secrets in development or test environments. Secrets shouldn't be deployed with the app. Using environment variables to store a production connection string is recommended against, as it's not the most secure approach. In complex app configuration scenarios, grouping and reading related hierarchical configuration data with the Options pattern is recommended.
- [ASP-003](../standards/aspnetcore.md) (must): Setting the minimum default log level in configuration, not in C# code, is recommended, and so is specifying log levels in configuration rather than in code with filter functions. If a logging data store is slow, don't write to it directly: consider writing the log messages to a fast store first and moving them to the slower store later. For example, don't write log messages directly to a SQL Server data store in a Log method, because Log methods are synchronous.
- [ASP-004](../standards/aspnetcore.md) (must): Don't store sensitive data in session state. The site should continue to function without the session data: critical application data should be stored in the user database and cached in session only as a performance optimization. SignalR apps shouldn't use session state. Never use query strings for sensitive data, and the app must always revalidate the data stored in hidden fields.
- [ASP-005](../standards/aspnetcore.md) (must): A best practice is to never change state on a GET request. Using AutoValidateAntiforgeryToken broadly for non-API scenarios is recommended. Don't disable CSRF protection on browser-accessible endpoints that rely on cookies for authentication.
- [ASP-006](../standards/aspnetcore.md) (must): Handle uploaded files safely: never use a client-supplied file name for saving a file to physical storage; when the app stores uploads on physical storage, never grant execute permission on the storage location; set a maximum size limit to prevent large uploads; do not persist uploaded files in the same directory tree as the app; and the uploaded file's extension should be checked against a list of permitted extensions. BLZ-022 adds the Blazor file-upload page's own advice.
- [ASP-007](../standards/aspnetcore.md) (must): Don't store files that require authorization in wwwroot and rely only on MapStaticAssets().RequireAuthorization() to protect them. Disabling directory browsing in production is highly recommended. Don't rely on file extension filtering to protect private files.
- [ASP-008](../standards/aspnetcore.md) (must): Apps should be written and tested to never depend on cached data: code should always have a fallback option to fetch the data. Don't insert external input into the cache, and avoid using external user input directly in cache keys. Do not cache user-specific data that may be retrieved by other user requests.
- [ASP-009](../standards/aspnetcore.md) (must): HTTP response caching should only be enabled for content that doesn't change based on a user's identity or whether a user is signed in. Responses containing content for authenticated clients must be marked as not cacheable, to prevent the response caching middleware from storing and serving them.
- [ASP-010](../standards/aspnetcore.md) (must): In controller-based APIs, prefer configuring authorization policies or writing a custom authorization policy over writing a custom filter, and prefer middleware for exception handling. Do not throw exceptions within authorization filters. Avoid creating and using filters purely for logging purposes.
- [ASP-011](../standards/aspnetcore.md) (must): For protection against overposting, view models are recommended rather than the [Bind] attribute. [BindProperty] should not be used on models containing properties that should not be changed by the client. Don't apply [FromBody] to more than one parameter per action method. For a string-to-type conversion that doesn't require external resources or multiple inputs, creating a type converter or using TryParse is recommended.
- [ASP-012](../standards/aspnetcore.md) (must): Controller-based web API controllers should typically derive from ControllerBase rather than Controller; if the same controller must support views and web APIs, derive from Controller. Don't use [FromRoute] when values might contain %2f (that is /); use [FromQuery] if the value might contain %2f.
- [ASP-015](../standards/aspnetcore.md) (must): Don't use route constraints for input validation: if constraints are used for input validation, invalid input results in a 404 Not Found response, and invalid input should produce a 400 Bad Request with an appropriate error message. SEC-010 and API-006 say how input is validated.
- [ASP-016](../standards/aspnetcore.md) (must): Do not suppress a warning from ASP0003, ASP0004, ASP0006, ASP0008, ASP0009, ASP0010 or BL0005. Using the types in the Microsoft.AspNetCore.Components.RenderTree namespace is not recommended in user code.
- [ASP-017](../standards/aspnetcore.md) (must): A gRPC channel should be reused when making gRPC calls. Prefer asynchronous programming with async and await when calling gRPC methods. Always dispose streaming calls once they're no longer needed. Configuring a gRPC call deadline is recommended. When calling gRPC services from an ASP.NET Core app, consider the gRPC client factory integration.
- [ASP-018](../standards/aspnetcore.md) (should): gRPC services should only listen and respond over secured ports, and exception messages shouldn't be exposed to the client in production apps. For gRPC services secured by client certificates, the Microsoft.AspNetCore.Authentication.Certificate package is recommended.
- [ASP-019](../standards/aspnetcore.md) (must): In SignalR hubs, don't store state in a property of the hub class, because each hub method call is executed on a new hub instance, and don't instantiate a hub directly via DI. You must ensure that a hub's methods don't execute concurrent database operations on the same context instance, because DbContext isn't thread-safe.
- [ASP-020](../standards/aspnetcore.md) (must): When SignalR runs on a server farm, sticky sessions must be used, and the Redis backplane is the recommended scale-out approach for apps hosted on your own infrastructure. In a SignalR app's CORS policy, allow the specific expected origins: allowing any origin is possible but not secure or recommended. Always use HTTPS between the client and the server, and exception messages should not be exposed to the client in production apps.
- [ASP-023](../standards/aspnetcore.md) (must): The Data Protection key ring should be protected using appropriate permissions, and its storage location should have its access limited to the app itself. When the app specifies an explicit key persistence location, specifying an explicit key encryption mechanism for production deployments is also recommended. The data protection stack must be configured to work in a server farm, and components that consume IDataProtectionProvider must pass a unique purposes parameter to the CreateProtector method.
- [ASP-024](../standards/aspnetcore.md) (must): A delegating handler for an HttpClient must be registered in DI as a transient service, rather than singleton or scoped.
- [CRF-013](../standards/craft.md) (must): Wherever the tests run the app, the container validates scopes and its registrations (ValidateScopes, ValidateOnBuild) in every environment they use, not only in Development, so a singleton that captures a scoped service, and a scoped service resolved from the root, fail a test; the app's own setting is left as it is. CRF-020 holds Microsoft's dependency injection guidelines.
- [DAT-002](../standards/data.md) (should): An app with a server relational database reaches it through EF Core, and its schema changes only through EF Core code-first migrations kept in the repo, never EnsureCreated (tests apply the migrations too, DAT-005); a test fails when the model has changes no migration covers.
- [DAT-003](../standards/data.md) (should): Every migration of a database that more than one version of the app can reach (a server database, not one on the user's device) keeps working with the version still running: a schema change is split into expand (add, in one release), migrate (move data and code over) and contract (drop or rename, in a later release, once no running version uses the old shape); each call in a migration's Up that drops, renames or alters something, changes data or runs raw SQL carries a '// DAT-003: <reason>' comment, directly above it or at the end of the line it starts on, saying why the running version still works.
- [DAT-005](../standards/data.md) (should): Integration and functional tests of an app with a server database, and its local development, run against the production database engine, in a container (Testcontainers for tests) or its official emulator (the Azure Cosmos DB emulator), with the app's migrations applied; never the EF Core in-memory provider, and never SQLite standing in for another engine.
- [DAT-006](../standards/data.md) (should): A cloud database starts on its free offer where the guide names one, with the setting that keeps it inside the free amount (Azure SQL Database: the free limit with AutoPause, which stops billing; Azure Cosmos DB: the free tier with a total throughput limit of 1000 RU/s, which caps throughput but not storage past 25 GB), plus a Cost Management budget alert, the only signal for what a setting can't stop; turning a guard off or moving to a paid tier is the owner's call (ARC-012, the cost rule).
- [DAT-007](../standards/data.md) (must): A connection to any cloud or server database, not only Azure SQL Database, retries transient failures with its provider's execution strategy (EnableRetryOnFailure for SQL Server and Azure SQL, or the provider's own), and where a retried commit could insert a row twice, keys are generated by the client.
- [DAT-013](../standards/data.md) (should): Use expand -> migrate -> contract schema changes to keep old and new app versions compatible during a transition.
- [DAT-014](../standards/data.md) (must): For automated deployment of EF Core migrations, use a migration bundle; use a SQL script instead when the SQL must be reviewed, modified, archived, or handed to a DBA before it is applied. Carefully consider before applying migrations at runtime in production; prefer a migration bundle for automation or a SQL script when review and approval are required, and don't make every application replica run migrations from its entrypoint. Use a separate identity for deployment that has permission to change the schema; the identity the application uses at run time should normally have only the permissions it needs to read and write data. Don't store production connection strings in source control or embed them in the bundle.
- [DAT-015](../standards/data.md) (should): An app that connects to Azure SQL Database should be built to expect transient errors, and implements retry logic for them instead of surfacing them to users as application errors. When code that uses a retrying EF Core execution strategy starts its own transaction, the solution is to invoke the execution strategy manually with a delegate representing everything that needs to be executed. Where an app lets a failed commit simply fail, it needs to avoid store-generated keys so that an exception is thrown instead of a duplicate row being added, and should consider a client-generated GUID or a client-side value generator.
- [HST-001](../standards/hosting.md) (should): Services with a scoped or transient lifetime should not be auto-activated, and auto-activated services should complete their initialization quickly to avoid delaying application startup; for longer-running initialization, consider background services or hosted services.
- [HST-004](../standards/hosting.md) (should): AddDistributedMemoryCache should only be used in development or testing scenarios; it isn't a viable production implementation of IDistributedCache.
- [OPS-001](../standards/operations.md) (must): Every ASP.NET Core app sends its logs, metrics and traces through OpenTelemetry, set up in one ServiceDefaults project, and exports them over OTLP when OTEL_EXPORTER_OTLP_ENDPOINT is set.
- [OPS-002](../standards/operations.md) (must): Every ASP.NET Core app maps /health (readiness: every check, its database included) and /alive (liveness: only checks tagged live) in every environment, answering with the status word only; a Healthy answer is cached briefly, and a slow check is cut off with a 504.
- [OPS-003](../standards/operations.md) (must): Every HttpClient comes from IHttpClientFactory and gets the standard resilience handler (timeouts, retries with backoff, circuit breaker) from the ServiceDefaults project, retrying only safe methods; a client that needs other settings removes the default handler (RemoveAllResilienceHandlers, experimental: suppress EXTEXP0001 with a reason) before adding its own. An app that needs cookies, which the factory's pooled handlers would share, keeps a long-lived HttpClient for each cookie container instead, over a SocketsHttpHandler with a PooledConnectionLifetime and wrapped in a ResilienceHandler, as the HttpClient guidelines page shows, decided by an ADR that also lifts the constructor ban there (CRF-010).
- [OPS-004](../standards/operations.md) (must): Every app keeps a runbook at docs/runbook.md, started from the kit's template: a Status line (Draft or In use), a Last reviewed date, a reference section on where it runs, and one how-to guide each for deploying a release, rolling one back, checking its health, reading its telemetry, restoring its data and responding to an incident; before the app's first production deployment every placeholder is filled in and the status set to In use, and the runbook is reviewed whenever how the app is deployed, hosted or stores data changes.
- [OPS-005](../standards/operations.md) (must): An app shuts down gracefully: on SIGTERM its host stops taking requests and gives in-flight work a shutdown timeout that ends before the platform's grace period (25 seconds where the platform allows 30, Kubernetes' default), and long-running work stops on the host's stopping token or the request's cancellation token, which every call passes on.
- [OPS-006](../standards/operations.md) (must): An app's settings are options validated when it starts (ValidateDataAnnotations or a validator, and ValidateOnStart), so bad configuration stops it at startup instead of failing requests later.
- [OPS-007](../standards/operations.md) (must): Avoid blocking calls; make hot code paths asynchronous, and call data access, I/O and long-running operations APIs asynchronously if an asynchronous API is available; avoid reading large request bodies or response bodies into memory; don't create and dispose of HttpClient instances directly, and use HttpClientFactory to retrieve them (OPS-008 names the lifetime options); don't use HttpContext after the request is complete, and don't access it from multiple threads. For high-performance logging scenarios in .NET 6 and later, use LoggerMessageAttribute with compile-time source generation.
- [OPS-009](../standards/operations.md) (should): When the host receives a shutdown signal (for example, Ctrl+C or StopAsync), it notifies the app by signaling ApplicationStopping; an app with long-running operations that need to finish gracefully should subscribe to that event.
- [OPS-010](../standards/operations.md) (should): In some hosting scenarios, use a pair of health checks to distinguish two app states: readiness (the app is running normally but isn't ready to receive requests) and liveness (the app has crashed and must be restarted).
- [OPS-012](../standards/operations.md) (must): Documentation should capture standard operating procedures and clearly define how work is done; standards should be regularly reviewed and challenged to ensure that they remain appropriate; use templates and version control to maintain consistency and keep a record of updates, and include authorship and review dates. An incident response plan should define the key roles involved in managing an incident and the responsibilities of each, and must include a communication and escalation structure and the core procedures the team will follow during detection, triage, containment and recovery; regularly test incident response processes using dry runs or chaos engineering exercises. Safe deployment practice (SDP) guidelines should provide clear instructions on how to deal with data changes according to the workload's data estate design.
- [OPS-013](../standards/operations.md) (should): Even if Data Protection APIs aren't called by user code, data protection should be configured to create a persistent cryptographic key store: the ASP.NET Core Data Protection stack is used by several ASP.NET Core middlewares, including authentication middleware (for example, cookie middleware) and cross-site request forgery (CSRF) protections.
- [OPS-016](../standards/operations.md) (should): When a systemd unit runs a .NET app, avoid setting KillSignal=SIGINT: .NET lifetime integrations listen for SIGTERM to start a graceful shutdown.
- [OPS-017](../standards/operations.md) (should): If the /health and /alive endpoints are enabled outside Development, it's recommended to protect them with routing features such as host filtering or authorization.
- [SEC-008](../standards/security.md) (should): An app never stores passwords or issues its own access tokens: users sign in with an OpenID Connect provider (Microsoft Entra ID or Entra External ID unless an ADR picks another), and an HTTP API accepts its access tokens with AddJwtBearer, which checks their signature, issuer, audience and lifetime, set under Authentication:Schemes:Bearer; development uses dotnet user-jwts, whose key stays in user secrets; ASP.NET Core Identity or any other scheme needs an ADR.
- [SEC-009](../standards/security.md) (should): Every read or change of a user's data is limited to that user's data in the query itself, in the application and data layers, not only in the endpoint; the user's id is the token's sub claim, which the fallback policy requires (unique within one issuer, so an app that trusts more than one keys on the issuer and sub together), and another user's item answers 404, as one that doesn't exist does.
- [SEC-010](../standards/security.md) (should): Every value a client sends is checked where it enters the app against what's allowed: required fields, a maximum length for every string, URI and collection, and a range for every number. A value outside those bounds gets a 400 validation problem that names the field; a domain rule's refusal is a 400 Problem (API-006); neither repeats the value. API-006 says how a Minimal API does it.
- [SEC-011](../standards/security.md) (must): Every ASP.NET Core app applies Microsoft's Kestrel production security checklist for where it's hosted, at the edge or behind a proxy: HTTPS only (at the edge, Kestrel terminates TLS 1.2 or later and serves no plain HTTP; behind a proxy, the proxy does), host filtering with its own AllowedHosts, HSTS outside Development, a rate limit for each caller, CORS only for named origins, a request body cap well under the 30 MB default, and no Server header; behind a proxy, forwarded headers only from KnownProxies or KnownIPNetworks, and never through ASPNETCORE_FORWARDEDHEADERS_ENABLED.
- [SEC-013](../standards/security.md) (must): An HTTP endpoint accepts and returns only Contracts types, never a domain entity, so a field added to the domain never reaches a client by accident.
- [SEC-017](../standards/security.md) (must): For a server-side app where most or all endpoints require authentication, set a fallback authorization policy that requires an authenticated user; it is secure by default and protects newly added endpoints. Apply AllowAnonymous to an endpoint that is intentionally public. ASVS 8.2.1: function-level access is restricted to consumers with explicit permissions.
- [SEC-018](../standards/security.md) (must): Don't generate your own access tokens or ID tokens, except for testing purposes; use OpenID Connect or an OAuth standard to create access tokens for API access, and you should not create an access token from a username and password request. JWT bearer tokens should be fully validated in an API (signature, issuer, audience and expiration), and the API should return 401 when any of them is incorrect. ASVS 9.1.1, 9.2.1 and 9.2.3 ask for the signature or MAC, validity time span and audience checks.
- [SEC-019](../standards/security.md) (must): Every API endpoint that receives an ID of an object and performs any action on the object should implement object-level authorization checks. Use the authorization mechanism to check that the logged-in user has access to perform the requested action on the record in every function that uses an input from the client to access a record in the database. ASVS 8.2.2 and 8.3.1: data-specific access is restricted to consumers with explicit permissions to specific data items, and authorization rules are enforced at a trusted service layer. To store information per user, use the sub or oid claim alone (with tid for routing or sharding if needed), and don't identify a user by human-readable data.
- [SEC-020](../standards/security.md) (must): Define and enforce a maximum size of data on all incoming parameters and payloads, such as maximum length for strings, maximum number of elements in arrays and maximum upload file size. Add server-side validation for query string and request body parameters, especially the one that controls the number of records returned. ASVS 2.2.1 and 2.2.2: input is validated to enforce business or functional expectations for that input, which should either use positive validation against an allow list of values, patterns and ranges or compare the input to an expected structure and logical limits, and input validation is enforced at a trusted service layer.
- [SEC-021](../standards/security.md) (must): Where Kestrel is an edge server, with no reverse proxy: use host-filtering middleware, enable HTTPS redirection, rate limiting must be handled by the application, don't enable the Forwarded Headers middleware, and verify ASPNETCORE_FORWARDEDHEADERS_ENABLED isn't set in edge deployments. Behind a reverse proxy, the Forwarded Headers middleware is required; configure KnownProxies or KnownIPNetworks explicitly. For an API that doesn't accept large uploads, consider lowering the request body limit significantly. Disable Kestrel's Server header (AddServerHeader) to prevent server identification. OWASP API4: limit how often a client can interact with the API within a defined timeframe (rate limiting).
- [SEC-022](../standards/security.md) (should): Most applications should strive for OWASP ASVS Level 2; Level 1 contains the minimum requirements to consider when securing an application and is a critical starting point.
- [SEC-023](../standards/security.md) (must): When an API endpoint exposes an object, always make sure the user should have access to each property you expose: avoid generic serialization methods and cherry-pick the properties to return, avoid (if possible) functions that automatically bind client input to objects, allow changes only to the properties the client should update, and keep returned data structures to the bare minimum.
<!-- end ruleset -->

## Consequences

- A Web API gets the core ruleset and the rules whose scope names `web-api`: the API, security, operations and ASP rules, EF Core's server-database rules (DAT-002, DAT-005, DAT-013, DAT-014) and the web hosting rules (HST-001, HST-004).
- The rules from the 2026-11-17 pages (ASP-001 to ASP-024 and others) are proposed. They aren't in force until the owner accepts them.
- **Gap:** The inventory's aspnetcore page lists pages with no rule. Two stand out for Web APIs: response compression (tuning detail) and certificate authentication (niche).

## Pillars affected

- **Security:** ASVS-aligned rules (SEC-008 to SEC-011, SEC-017 to SEC-023) and ASP's CSRF, upload and data protection rules apply to server-side web apps.
- **Reliability:** health probes, resilience and graceful shutdown (OPS rules).
- **Operational Excellence:** logging and configuration rules (ASP-002, ASP-003).
- **Performance Efficiency:** caching and gRPC client rules (ASP-008, ASP-009, ASP-017).
