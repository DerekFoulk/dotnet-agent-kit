# ADR-0093: Windows Forms ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A Windows Forms app is a Windows desktop app built on the Windows Forms designer and .NET. Its `project-types.yml` entry is `winforms` (Windows Forms), and its docs start at <https://learn.microsoft.com/dotnet/desktop/winforms/overview/>. Windows Forms serves Windows alone and is the older stack, so ARC-014 asks a new Windows Forms app for an ADR saying why.

ADR-0082 makes every rule name the project types it applies to. ADR-0084 gives an app only the common ruleset plus the rulesets of its project types. This ADR records the ruleset for `winforms` (Windows Forms), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/desktop.md`):

- <https://learn.microsoft.com/dotnet/desktop/winforms/advanced/how-to-retrieve-data-from-the-clipboard>: TryGetData and the JSON methods; BinaryFormatter not recommended (WFM-001).
- <https://learn.microsoft.com/dotnet/desktop/winforms/forms/events>: try-catch in async event handlers; never block in UI code (WFM-002).
- <https://learn.microsoft.com/dotnet/desktop/winforms/advanced/walkthrough-creating-an-accessible-windows-based-application>: high contrast, access keys, tab order, test accessibility (WFM-003).
- <https://learn.microsoft.com/dotnet/desktop/winforms/controls/best-practices-for-scaling-the-windows-forms-datagridview-control>: no per-cell styles or auto-size on many rows (WFM-004).
- <https://learn.microsoft.com/windows/apps/get-started/best-practices>: no admin rights; installer behavior; signing (WUI-018, WUI-019, WUI-021).

WFM-002 is stricter than STY-011, which allows GetAwaiter().GetResult() where await can't reach. The Windows Forms page says never to block in UI code.

WFM-001 to WFM-004 name `winforms` alone. WUI-018, WUI-019 and WUI-021 also name it, as do ARC-010, ARC-011, ARC-014, UI-001 and UI-003.

## Options

### Option 1: A ruleset for Windows Forms

- **Trade-offs:** An app of this type gets the common rules plus the rules that name `winforms`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `projectTypes` list per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `projectTypes` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a desktop app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `winforms` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the project-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

## The ruleset

<!-- ruleset: winforms -->
- [ARC-010](../standards/architecture.md) (proposed): In MAUI and desktop apps, view models and all other logic live in UI-independent libraries (ARC-003); a UI project, one that sets UseMaui, UseWPF, UseWindowsForms or UseWinUI, holds only views, platform code and startup wiring, no other project references it, and the coverage gate exempts it.
- [ARC-011](../standards/architecture.md) (proposed): A new general-purpose Windows desktop app is recommended to use WinUI 3, the native UI framework delivered with the Windows App SDK; a team expecting to target several platforms should start with .NET MAUI (Microsoft names React Native for Desktop beside it), which uses WinUI 3 when running on Windows.
- [ARC-014](../standards/architecture.md) (proposed): A new desktop app uses the framework ARC-011 names for its platforms (WinUI 3 for a Windows desktop app, .NET MAUI for several platforms); a new WPF or Windows Forms app needs an ADR that says why.
- [UI-001](../standards/ui.md) (proposed): Every UI an app ships meets WCAG 2.2 level AA: web UI (Blazor, Razor) as written, native UI (MAUI, desktop) as W3C's WCAG2ICT note applies it. Building UI, an agent checks at least the success criteria UI-003 lists, keeping each one's own exceptions, such as a link inside a sentence or a data table that needs two dimensions.
- [UI-003](../standards/ui.md) (proposed): To meet WCAG 2.2 level AA, a UI must meet, among all the other level A and AA success criteria: a text alternative for non-text content, and a name for every control (1.1.1); structure and relationships that can be programmatically determined (1.3.1); color not as the only visual means of conveying information (1.4.1); a contrast ratio of at least 4.5:1 for text, 3:1 for large text (1.4.3); text resizable to 200 percent without loss of content or functionality (1.4.4); content that reflows at a width equivalent to 320 CSS pixels (1.4.10); a contrast ratio of at least 3:1 for the visual information that identifies user interface components and states (1.4.11); all functionality operable through a keyboard interface (2.1.1) with no keyboard trap (2.1.2); a focus order that preserves meaning and operability (2.4.3); a visible keyboard focus indicator (2.4.7) that isn't entirely hidden by author-created content (2.4.11); pointer targets at least 24 by 24 CSS pixels unless an exception applies (2.5.8); labels or instructions where content requires input (3.3.2); no cognitive function test in authentication unless an alternative or a mechanism is offered (3.3.8); and a programmatically determinable name and role for every user interface component (4.1.2). For native UI, W3C's WCAG2ICT note says how each criterion applies.
- [WFM-001](../standards/winforms.md) (proposed): Use the type-safe TryGetData<T> method, not the obsolete GetData, for custom clipboard data in Windows Forms on .NET 10, and prefer the JSON-based SetDataAsJson<T> and TryGetData<T> for custom formats. BinaryFormatter clipboard support isn't recommended: use it only as a temporary migration bridge, and if you do, you must implement type resolvers that restrict deserialization to explicitly approved types.
- [WFM-002](../standards/winforms.md) (proposed): In Windows Forms async event handlers, always wrap awaited operations in try-catch blocks. Never use blocking calls such as .Wait(), .Result or .GetAwaiter().GetResult() in event handlers or any UI code.
- [WFM-003](../standards/winforms.md) (proposed): Support Windows accessibility in a Windows Forms app. When SystemInformation.HighContrast is true, display all UI elements with the system color scheme, convey by visual cues or sound any information conveyed through color, and omit images or patterns behind text; check the setting at startup, respond to the UserPreferenceChanged system event, and release that event when the app closes. Avoid conveying important information by sound alone. Create access keys with the & character, put a text box's label immediately before it in the tab order, and set a font size of 10 points or larger if it isn't adjustable. Test the accessibility features before deploying.
- [WFM-004](../standards/winforms.md) (proposed): When a Windows Forms DataGridView displays large amounts of data, follow the page's scaling guidelines to avoid consuming large amounts of memory or degrading UI responsiveness. Avoid setting cell style properties on individual cells or rows, avoid creating shortcut menus for individual cells and rows, and avoid automatic sizing on a large set of rows; if you do use automatic sizing, only resize based on the displayed rows.
- [WUI-018](../standards/winui.md) (proposed): A Windows desktop app must not require administrative privileges to install or run; where a feature needs them, consider a separate process for it. Use your language or framework's standard libraries for cryptography, never your own, and always use secured connections such as TLS when transmitting data. Always get the user's consent before collecting and storing personal data.
- [WUI-019](../standards/winui.md) (proposed): An installer for a Windows desktop app shouldn't leave temporary files behind, and should avoid requiring elevated permissions or operating system reboots where possible. Consider MSIX for a seamless install, update and uninstall, and consider letting users preserve their data when they uninstall.
- [WUI-021](../standards/winui.md) (proposed): Sign all the files of a Windows app distributed outside the Microsoft Store with a valid certificate; unsigned files build SmartScreen reputation anew with every update. Azure Artifact Signing is Microsoft's recommended code signing service for that case.

## Consequences

- A Windows Forms app gets the common ruleset, WFM-001 to WFM-004 and the Windows desktop rules above, and an ADR is required for choosing Windows Forms (ARC-014).
- WFM-001 to WFM-004 are proposed.
- **Gap:** Two security pages describe .NET Framework code access security and partial trust, so they have no rule. The virtual mode and TableLayoutPanel pages are descriptive or UX choices.

## Pillars affected

- **Reliability:** async handler and clipboard rules (WFM-001, WFM-002).
- **Performance Efficiency:** DataGridView scaling (WFM-004).
- **Security:** clipboard serialization, no admin rights (WFM-001, WUI-018).
