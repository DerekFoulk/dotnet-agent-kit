# ADR-0087: Blazor ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A Blazor Web App is an ASP.NET Core app whose UI is Razor components, rendered on the server, in the browser, or both. Its `app-types.yml` entry is `blazor` (Blazor Web App), and its docs start at <https://learn.microsoft.com/aspnet/core/blazor/>.

ADR-0084 makes every rule name its `scope`, `core` or the app types it applies to, and gives an app only the core ruleset (ADR-0085) plus the rulesets of its app types. This ADR records the ruleset for `blazor` (Blazor Web App), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/aspnetcore.md`):

- <https://learn.microsoft.com/aspnet/core/blazor/components/render-modes>: design components to work in any render mode (BLZ-001).
- <https://learn.microsoft.com/aspnet/core/blazor/components/>: components do not write their own parameters; no raw HTML from untrusted sources (BLZ-002, BLZ-012).
- <https://learn.microsoft.com/aspnet/core/blazor/components/synchronization-context>: avoid thread-blocking calls; update from external events on the context (BLZ-004).
- <https://learn.microsoft.com/aspnet/core/blazor/components/component-disposal>: unsubscribe handlers and dispose objects (BLZ-005).
- <https://learn.microsoft.com/aspnet/core/blazor/performance/rendering>: avoid thousands of component instances and needless re-rendering (BLZ-008).
- <https://learn.microsoft.com/aspnet/core/blazor/javascript-interoperability/>: async JS interop on the server; no inline handlers (BLZ-009, BLZ-010).
- <https://learn.microsoft.com/aspnet/core/blazor/fundamentals/dependency-injection>: scoped services and component lifetimes (BLZ-018).
- <https://learn.microsoft.com/aspnet/core/blazor/fundamentals/handle-errors>: no exception details in the UI in production (BLZ-019).
- <https://learn.microsoft.com/aspnet/core/blazor/forms/>: form names and overposting (BLZ-021).
- <https://learn.microsoft.com/aspnet/core/blazor/file-uploads>: do not read a whole stream into memory (BLZ-022).
- <https://learn.microsoft.com/aspnet/core/blazor/security/content-security-policy>: use a Content Security Policy (BLZ-013).
- <https://learn.microsoft.com/aspnet/core/blazor/security/interactive-server-side-rendering>: limits before CPU-heavy work; session affinity (BLZ-011, BLZ-024).
- <https://learn.microsoft.com/aspnet/core/blazor/state-management/prerendered-state-persistence>: no sensitive data in persisted prerender state (BLZ-020).
- <https://learn.microsoft.com/aspnet/core/blazor/tooling>: start with a Blazor Web App (BLZ-024).

Blazor Web Apps are also ASP.NET Core apps, so the shared web rules (most ASP rules, and the API, SEC and OPS rules for web apps) name `blazor` with `web-api`. Blazor Hybrid isn't a supported app type yet (ADR-0084), so the BLZ rules name `blazor` alone.

## Options

### Option 1: A ruleset for Blazor Web App

- **Trade-offs:** An app of this type gets the core rules plus the rules whose scope names `blazor`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `scope` per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `scope` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a .NET MAUI app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `blazor` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the app-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

- [API-001](../standards/api-design.md) (proposed): An app's API style is chosen in its plan: an HTTP API with Minimal APIs by default; gRPC, SignalR, controllers or GraphQL only where a Microsoft page recommends that style for the app's scenario (API-008) or the owner asks for it by name, and the plan says which.
- [API-008](../standards/api-design.md) (proposed): For new ASP.NET Core API projects, Minimal APIs are recommended; consider controller-based APIs if you need model binding extensibility, form binding support (including IFormFile), advanced validation features, application parts or the application model, or OData support. gRPC is well suited to microservices, point-to-point real-time communication, polyglot environments, network-constrained environments and inter-process communication; other frameworks are recommended over gRPC for browser-accessible APIs and for broadcast real-time communication, and SignalR is a useful framework for broadcasting.
- [API-002](../standards/api-design.md) (accepted): Every HTTP API error response is Problem Details (RFC 9457): AddProblemDetails, UseExceptionHandler and UseStatusCodePages; a client error such as malformed input stays a 400 in every environment, and outside Development a 500 never carries the exception's message or stack.
- [API-003](../standards/api-design.md) (accepted): An HTTP API describes itself with the built-in OpenAPI document (Microsoft.AspNetCore.OpenApi) and typed results; the document, and any UI for it such as Scalar or Swagger UI, is mapped in Development only; a contract test snapshots the document, so every change to the API shows in review.
- [API-004](../standards/api-design.md) (accepted): Every HTTP endpoint that lists a collection pages it in the data store, in a deterministic order, with limit (default 25, at most 100) and offset (at most 10,000) query parameters, and answers an object with the page's items and a nextLink to the next page, null on the last page or the last one the offset cap allows.
- [API-005](../standards/api-design.md) (proposed): An HTTP API isn't versioned until its first breaking change to a contract that another app or a released client depends on; that change gets an ADR that picks how versions are told apart (URI, query string or header) and the package, a new version, and the earlier version stays until its callers move.
- [API-007](../standards/api-design.md) (accepted): In an HTTP API, when possible, base resource URIs on nouns and not verbs, and avoid using verbs in URIs to represent operations; a POST that creates a resource synchronously should return 201 Created and identify the resource in the Location header; GET, HEAD, PUT and DELETE must be idempotent; and for work that takes time, consider making the method asynchronous: an asynchronous method should return 202 Accepted, include the status endpoint's URI in the 202's Location header, and if the operation creates a new resource, the status endpoint should return 303 See Other after it completes, with a Location header that gives the new resource's URI.
- [API-009](../standards/api-design.md) (accepted): OpenAPI user interfaces (Swagger UI, ReDoc, Scalar) should only be enabled in development environments.
- [API-010](../standards/api-design.md) (accepted): In non-development environments, use the exception handler middleware to produce an error payload. Don't enable the Developer Exception Page unless the app is running in the Development environment, and don't share detailed exception information publicly when the app runs in production.
- [API-011](../standards/api-design.md) (accepted): For an endpoint that returns a collection, use limit and offset query parameters with meaningful defaults, such as limit=25 and offset=0, and consider an upper limit on the number of items returned. Apply pagination in the data store, not after loading the entire collection, with a deterministic sort order; include a next-page link or continuation token in the response, omitted or null on the last page; and for a large or frequently changing collection, evaluate cursor-based pagination.
- [API-012](../standards/api-design.md) (proposed): Support versioning in the API contract: when you introduce a breaking API change, introduce a new API version, continue to support the previous version, and let clients select which version to call. Make API changes backward compatible when possible.
- [API-013](../standards/api-design.md) (accepted): An HTTP API's URIs name a collection with a plural noun, and use a verb sparingly, only for an operation that isn't a resource.
- [ARC-001](../standards/architecture.md) (accepted): Web apps use Clean Architecture in one deployable app; each distinct business area is a module with Domain, Application, Infrastructure, Presentation and Contracts projects, and Application code is grouped by feature; a project can deviate by ADR.
- [ARC-002](../standards/architecture.md) (accepted): Modules talk to each other only through their Contracts projects; a module never reads or writes another module's tables, and an app never shares its database with another app.
- [ARC-016](../standards/architecture.md) (proposed): ASP.NET Core's built-in use of and support for dependency injection makes Clean Architecture the most appropriate way to structure non-trivial monolithic applications. In it, the Application Core holds the business model, including the interfaces for operations performed using Infrastructure; Infrastructure's services should implement interfaces defined in the Application Core; and the UI project should reference the Application Core project, and its types should interact with infrastructure strictly through interfaces defined in Application Core.
- [ASP-001](../standards/aspnetcore.md) (proposed): Prefer requesting dependencies as constructor parameters over resolving services from RequestServices. Services resolved from the container should never be disposed by the developer. CRF-020 carries the rest of Microsoft's dependency injection guidance (the service locator pattern, stateful static classes and members, direct instantiation of dependent classes).
- [ASP-002](../standards/aspnetcore.md) (proposed): Never store passwords or other sensitive data in configuration provider code or in plain text configuration files, and don't use production secrets in development or test environments. Secrets shouldn't be deployed with the app. Using environment variables to store a production connection string is recommended against, as it's not the most secure approach. In complex app configuration scenarios, grouping and reading related hierarchical configuration data with the Options pattern is recommended.
- [ASP-003](../standards/aspnetcore.md) (proposed): Setting the minimum default log level in configuration, not in C# code, is recommended, and so is specifying log levels in configuration rather than in code with filter functions. If a logging data store is slow, don't write to it directly: consider writing the log messages to a fast store first and moving them to the slower store later. For example, don't write log messages directly to a SQL Server data store in a Log method, because Log methods are synchronous.
- [ASP-004](../standards/aspnetcore.md) (proposed): Don't store sensitive data in session state. The site should continue to function without the session data: critical application data should be stored in the user database and cached in session only as a performance optimization. SignalR apps shouldn't use session state. Never use query strings for sensitive data, and the app must always revalidate the data stored in hidden fields.
- [ASP-005](../standards/aspnetcore.md) (proposed): A best practice is to never change state on a GET request. Using AutoValidateAntiforgeryToken broadly for non-API scenarios is recommended. Don't disable CSRF protection on browser-accessible endpoints that rely on cookies for authentication.
- [ASP-006](../standards/aspnetcore.md) (proposed): Handle uploaded files safely: never use a client-supplied file name for saving a file to physical storage; when the app stores uploads on physical storage, never grant execute permission on the storage location; set a maximum size limit to prevent large uploads; do not persist uploaded files in the same directory tree as the app; and the uploaded file's extension should be checked against a list of permitted extensions. BLZ-022 adds the Blazor file-upload page's own advice.
- [ASP-007](../standards/aspnetcore.md) (proposed): Don't store files that require authorization in wwwroot and rely only on MapStaticAssets().RequireAuthorization() to protect them. Disabling directory browsing in production is highly recommended. Don't rely on file extension filtering to protect private files.
- [ASP-008](../standards/aspnetcore.md) (proposed): Apps should be written and tested to never depend on cached data: code should always have a fallback option to fetch the data. Don't insert external input into the cache, and avoid using external user input directly in cache keys. Do not cache user-specific data that may be retrieved by other user requests.
- [ASP-015](../standards/aspnetcore.md) (proposed): Don't use route constraints for input validation: if constraints are used for input validation, invalid input results in a 404 Not Found response, and invalid input should produce a 400 Bad Request with an appropriate error message. SEC-010 and API-006 say how input is validated.
- [ASP-016](../standards/aspnetcore.md) (proposed): Do not suppress a warning from ASP0003, ASP0004, ASP0006, ASP0008, ASP0009, ASP0010 or BL0005. Using the types in the Microsoft.AspNetCore.Components.RenderTree namespace is not recommended in user code.
- [ASP-019](../standards/aspnetcore.md) (proposed): In SignalR hubs, don't store state in a property of the hub class, because each hub method call is executed on a new hub instance, and don't instantiate a hub directly via DI. You must ensure that a hub's methods don't execute concurrent database operations on the same context instance, because DbContext isn't thread-safe.
- [ASP-020](../standards/aspnetcore.md) (proposed): When SignalR runs on a server farm, sticky sessions must be used, and the Redis backplane is the recommended scale-out approach for apps hosted on your own infrastructure. In a SignalR app's CORS policy, allow the specific expected origins: allowing any origin is possible but not secure or recommended. Always use HTTPS between the client and the server, and exception messages should not be exposed to the client in production apps.
- [ASP-021](../standards/aspnetcore.md) (proposed): For a web app that signs users in with OpenID Connect, the recommended way is a confidential client using the code flow, and using PKCE with it is recommended. Public OpenID Connect/OAuth clients are no longer recommended for web applications. For a web app with no independent backend, the Backend for Frontend (BFF) pattern is recommended. When authenticating with one of the Microsoft identity providers, the Microsoft.Identity.Web NuGet packages are recommended. Don't deploy an app with IdentityModelEventSource.ShowPII to productive servers.
- [ASP-023](../standards/aspnetcore.md) (proposed): The Data Protection key ring should be protected using appropriate permissions, and its storage location should have its access limited to the app itself. When the app specifies an explicit key persistence location, specifying an explicit key encryption mechanism for production deployments is also recommended. The data protection stack must be configured to work in a server farm, and components that consume IDataProtectionProvider must pass a unique purposes parameter to the CreateProtector method.
- [ASP-024](../standards/aspnetcore.md) (proposed): A delegating handler for an HttpClient must be registered in DI as a transient service, rather than singleton or scoped.
- [BLZ-001](../standards/blazor.md) (proposed): Component authors should avoid coupling a component's implementation to a specific render mode, and should typically design components to support any render mode or hosting model. In most cases, reusable component authors should not specify a render mode, even when interactivity is required.
- [BLZ-002](../standards/blazor.md) (proposed): Generally, avoid creating components that write directly to their own component parameters. Component parameters should be declared as auto properties, with no custom logic in their get or set accessors. Don't use the required modifier or an init accessor on component parameter properties.
- [BLZ-003](../standards/blazor.md) (proposed): For two-way data binding, the @bind:get/@bind:set modifiers are recommended. Specifying a culture with @bind:culture isn't recommended when using the date and number field types.
- [BLZ-004](../standards/blazor.md) (proposed): Avoid thread-blocking calls in components. When a component must be updated from an external event, such as a timer or other notification, use InvokeAsync to dispatch the work to Blazor's synchronization context.
- [BLZ-005](../standards/blazor.md) (proposed): Always unsubscribe event handlers from .NET events, and always dispose objects a component creates on the .NET side to avoid leaking managed memory.
- [BLZ-006](../standards/blazor.md) (proposed): Prefer .razor files and let the compiler deal with sequence numbers; manual render tree builder logic is advanced and unsafe, and not recommended for general component development.
- [BLZ-007](../standards/blazor.md) (proposed): Avoid creating a single large class that represents the entire global application state; prefer granular classes cascaded separately, each with specific subscriptions, so only the components that use a portion of the state are affected when it changes.
- [BLZ-008](../standards/blazor.md) (proposed): Avoid thousands of component instances. For components that render at scale, such as each item in a large list or the cells of a grid, try to avoid attribute splatting. Avoid recreating delegates for many repeated elements or components, and don't trigger events too rapidly. Most Razor components don't require aggressive optimization efforts, because most components don't repeat in the UI and don't rerender at high frequency.
- [BLZ-009](../standards/blazor.md) (proposed): Avoiding inline event handlers in favor of assigning handlers in JavaScript with addEventListener is recommended. JS collocation combined with JS modules is recommended, and inline JavaScript isn't recommended for Blazor apps. Maintaining a reference to a JSObjectReference requires disposing of it, to avoid leaking JS memory on the client. Don't execute JS interop code for DOM cleanup tasks during component disposal or when handling location changes. Avoid excessively fine-grained JS interop calls.
- [BLZ-010](../standards/blazor.md) (proposed): When adopting server-side rendering, JS interop calls must be asynchronous, and for server-side components the asynchronous invokeMethodAsync is recommended over the synchronous invokeMethod. In server-side apps with server interactivity, JS interop may fail due to networking errors and should be treated as unreliable.
- [BLZ-011](../standards/blazor.md) (proposed): In interactive server-side Blazor, the app must include appropriate checks and limits before performing potentially CPU-intensive work, and, as a general recommendation, clients shouldn't be permitted to allocate an unbounded amount of memory. Always validate data when handling events, don't trust calls from JavaScript to .NET methods, and don't make authorization decisions based on the state of the UI, only from component state.
- [BLZ-012](../standards/blazor.md) (proposed): Rendering raw HTML constructed from any untrusted source should always be avoided, and so should rendering HTML content directly from a database. Avoid passing user-supplied data in parameters to JavaScript calls; for example, don't write user-supplied data to the DOM by setting an element's innerHTML property. Avoid using user input as part of navigation call arguments.
- [BLZ-013](../standards/blazor.md) (proposed): A Content Security Policy (CSP) is recommended for Blazor apps. Avoid setting the frame-ancestors directive value to 'null' when WebSocket compression is enabled (compression is the default), because it makes the app vulnerable to malicious script injection and clickjacking attacks.
- [BLZ-014](../standards/blazor.md) (proposed): Don't implement authorization checks in client-side code if enforcement must be guaranteed; always perform authorization checks on the server within any API endpoints a client-side app accesses. Don't store app secrets, connection strings, credentials, passwords, PINs, private .NET/C# code or private keys and tokens in client-side code.
- [BLZ-015](../standards/blazor.md) (proposed): ASP.NET Core apps that use ASP.NET Core Identity for user management should use Razor Pages instead of Razor components for Identity-related UI, such as user registration, login, logout and other user management tasks. Building Razor components that directly handle Identity tasks isn't recommended or supported by Microsoft.
- [BLZ-016](../standards/blazor.md) (proposed): Production web apps and web APIs should use a production distributed token cache (for example Redis, SQL Server or Azure Cosmos DB). Always replace the in-memory distributed token caches with a real token cache provider when deploying the app to a production environment.
- [BLZ-017](../standards/blazor.md) (proposed): Components that use the interactive WebAssembly and Auto render modes should be designed so that they run successfully from both the client and the server. If such a component must call a server project-based API, or transform a request to an external web API, when running on the client, the recommended approach is to abstract that API call behind a service interface and implement client and server versions of the service.
- [BLZ-018](../standards/blazor.md) (proposed): Don't directly inject a scoped service into a component if you intend the service lifetime to match the lifetime of the component.
- [BLZ-019](../standards/blazor.md) (proposed): In production, don't render framework exception messages or stack traces in the UI. Narrowly scoping error boundaries is recommended in most scenarios.
- [BLZ-020](../standards/blazor.md) (proposed): During client-side rendering (CSR, InteractiveWebAssembly), state persisted during prerendering is exposed to the browser and must not contain sensitive, private information. To improve the user experience, begin by implementing streaming rendering, to avoid waiting for an asynchronous task to complete while prerendering.
- [BLZ-021](../standards/blazor.md) (proposed): Always use the @formname directive attribute with a unique form name. To mitigate overposting, using a separate view model or data transfer object (DTO) for the form and the database in create (insert) and update operations is recommended.
- [BLZ-022](../standards/blazor.md) (proposed): Outside of processing a small file, avoid reading the incoming file stream directly into memory all at once. Don't receive files from users or other untrusted sources and then make them available for immediate download without performing security checks on them. ASP-006 covers the rest of safe upload handling, including never using a client-supplied file name for saving a file.
- [BLZ-023](../standards/blazor.md) (proposed): To avoid .NET trimming problems in scenarios that rely on reflection, such as JS interop and JSON serialization, use custom types defined in non-trimmable libraries or preserve the types through linker configuration. In most cases, don't disable integrity checking of a Blazor WebAssembly app's downloaded resources.
- [BLZ-024](../standards/blazor.md) (proposed): A Blazor Web App is recommended for all new Blazor development in .NET 8 or later. For interactive server-side rendering, WebSockets is the recommended transport protocol, and selecting a proxy or gateway that supports WebSockets is recommended. Server-side Blazor Web Apps hosted in a web farm or cluster of machines must adopt session affinity to maintain Blazor circuits.
- [BLZ-025](../standards/blazor.md) (proposed): If the app should localize resources based on storing a user's culture setting, use a localization culture cookie.
- [BLZ-026](../standards/blazor.md) (proposed): Never reference the MAUI library from a Razor class library (RCL). RCLs should adopt host-agnostic design and shouldn't depend on specific hosting infrastructure or platform APIs. For an RCL's abstractions, prefer interfaces over abstract classes for flexibility.
- [CRF-013](../standards/craft.md) (accepted): Wherever the tests run the app, the container validates scopes and its registrations (ValidateScopes, ValidateOnBuild) in every environment they use, not only in Development, so a singleton that captures a scoped service, and a scoped service resolved from the root, fail a test; the app's own setting is left as it is. CRF-020 holds Microsoft's dependency injection guidelines.
- [DAT-002](../standards/data.md) (proposed): An app with a server relational database reaches it through EF Core, and its schema changes only through EF Core code-first migrations kept in the repo, never EnsureCreated (tests apply the migrations too, DAT-005); a test fails when the model has changes no migration covers.
- [DAT-003](../standards/data.md) (proposed): Every migration of a database that more than one version of the app can reach (a server database, not one on the user's device) keeps working with the version still running: a schema change is split into expand (add, in one release), migrate (move data and code over) and contract (drop or rename, in a later release, once no running version uses the old shape); each call in a migration's Up that drops, renames or alters something, changes data or runs raw SQL carries a '// DAT-003: <reason>' comment, directly above it or at the end of the line it starts on, saying why the running version still works.
- [DAT-005](../standards/data.md) (proposed): Integration and functional tests of an app with a server database, and its local development, run against the production database engine, in a container (Testcontainers for tests) or its official emulator (the Azure Cosmos DB emulator), with the app's migrations applied; never the EF Core in-memory provider, and never SQLite standing in for another engine.
- [DAT-006](../standards/data.md) (proposed): A cloud database starts on its free offer where the guide names one, with the setting that keeps it inside the free amount (Azure SQL Database: the free limit with AutoPause, which stops billing; Azure Cosmos DB: the free tier with a total throughput limit of 1000 RU/s, which caps throughput but not storage past 25 GB), plus a Cost Management budget alert, the only signal for what a setting can't stop; turning a guard off or moving to a paid tier is the owner's call (ARC-012, the cost rule).
- [DAT-007](../standards/data.md) (accepted): A connection to any cloud or server database, not only Azure SQL Database, retries transient failures with its provider's execution strategy (EnableRetryOnFailure for SQL Server and Azure SQL, or the provider's own), and where a retried commit could insert a row twice, keys are generated by the client.
- [DAT-013](../standards/data.md) (proposed): Use expand -> migrate -> contract schema changes to keep old and new app versions compatible during a transition.
- [DAT-014](../standards/data.md) (proposed): For automated deployment of EF Core migrations, use a migration bundle; use a SQL script instead when the SQL must be reviewed, modified, archived, or handed to a DBA before it is applied. Carefully consider before applying migrations at runtime in production; prefer a migration bundle for automation or a SQL script when review and approval are required, and don't make every application replica run migrations from its entrypoint. Use a separate identity for deployment that has permission to change the schema; the identity the application uses at run time should normally have only the permissions it needs to read and write data. Don't store production connection strings in source control or embed them in the bundle.
- [DAT-015](../standards/data.md) (accepted): An app that connects to Azure SQL Database should be built to expect transient errors, and implements retry logic for them instead of surfacing them to users as application errors. When code that uses a retrying EF Core execution strategy starts its own transaction, the solution is to invoke the execution strategy manually with a delegate representing everything that needs to be executed. Where an app lets a failed commit simply fail, it needs to avoid store-generated keys so that an exception is thrown instead of a duplicate row being added, and should consider a client-generated GUID or a client-side value generator.
- [HST-001](../standards/hosting.md) (proposed): Services with a scoped or transient lifetime should not be auto-activated, and auto-activated services should complete their initialization quickly to avoid delaying application startup; for longer-running initialization, consider background services or hosted services.
- [HST-004](../standards/hosting.md) (proposed): AddDistributedMemoryCache should only be used in development or testing scenarios; it isn't a viable production implementation of IDistributedCache.
- [OPS-001](../standards/operations.md) (accepted): Every ASP.NET Core app sends its logs, metrics and traces through OpenTelemetry, set up in one ServiceDefaults project, and exports them over OTLP when OTEL_EXPORTER_OTLP_ENDPOINT is set.
- [OPS-002](../standards/operations.md) (accepted): Every ASP.NET Core app maps /health (readiness: every check, its database included) and /alive (liveness: only checks tagged live) in every environment, answering with the status word only; a Healthy answer is cached briefly, and a slow check is cut off with a 504.
- [OPS-003](../standards/operations.md) (accepted): Every HttpClient comes from IHttpClientFactory and gets the standard resilience handler (timeouts, retries with backoff, circuit breaker) from the ServiceDefaults project, retrying only safe methods; a client that needs other settings removes the default handler (RemoveAllResilienceHandlers, experimental: suppress EXTEXP0001 with a reason) before adding its own. An app that needs cookies, which the factory's pooled handlers would share, keeps a long-lived HttpClient for each cookie container instead, over a SocketsHttpHandler with a PooledConnectionLifetime and wrapped in a ResilienceHandler, as the HttpClient guidelines page shows, decided by an ADR that also lifts the constructor ban there (CRF-010).
- [OPS-004](../standards/operations.md) (proposed): Every app keeps a runbook at docs/runbook.md, started from the kit's template: a Status line (Draft or In use), a Last reviewed date, a reference section on where it runs, and one how-to guide each for deploying a release, rolling one back, checking its health, reading its telemetry, restoring its data and responding to an incident; before the app's first production deployment every placeholder is filled in and the status set to In use, and the runbook is reviewed whenever how the app is deployed, hosted or stores data changes.
- [OPS-005](../standards/operations.md) (accepted): An app shuts down gracefully: on SIGTERM its host stops taking requests and gives in-flight work a shutdown timeout that ends before the platform's grace period (25 seconds where the platform allows 30, Kubernetes' default), and long-running work stops on the host's stopping token or the request's cancellation token, which every call passes on.
- [OPS-006](../standards/operations.md) (accepted): An app's settings are options validated when it starts (ValidateDataAnnotations or a validator, and ValidateOnStart), so bad configuration stops it at startup instead of failing requests later.
- [OPS-007](../standards/operations.md) (accepted): Microsoft's ASP.NET Core best practices say: avoid blocking calls; make hot code paths asynchronous, and call data access, I/O and long-running operations APIs asynchronously if an asynchronous API is available; avoid reading large request bodies or response bodies into memory; don't create and dispose of HttpClient instances directly, and use HttpClientFactory to retrieve them (OPS-008 names the lifetime options); don't use HttpContext after the request is complete, and don't access it from multiple threads. For high-performance logging scenarios in .NET 6 and later, use LoggerMessageAttribute with compile-time source generation.
- [OPS-009](../standards/operations.md) (accepted): When the host receives a shutdown signal (for example, Ctrl+C or StopAsync), it notifies the app by signaling ApplicationStopping; an app with long-running operations that need to finish gracefully should subscribe to that event.
- [OPS-010](../standards/operations.md) (accepted): In some hosting scenarios, use a pair of health checks to distinguish two app states: readiness (the app is running normally but isn't ready to receive requests) and liveness (the app has crashed and must be restarted).
- [OPS-012](../standards/operations.md) (proposed): The Well-Architected Framework's operational excellence pillar says: documentation should capture standard operating procedures and clearly define how work is done; standards should be regularly reviewed and challenged to ensure that they remain appropriate; use templates and version control to maintain consistency and keep a record of updates, and include authorship and review dates. An incident response plan should define the key roles involved in managing an incident and the responsibilities of each, and must include a communication and escalation structure and the core procedures the team will follow during detection, triage, containment and recovery; regularly test incident response processes using dry runs or chaos engineering exercises. Safe deployment practice (SDP) guidelines should provide clear instructions on how to deal with data changes according to the workload's data estate design.
- [OPS-013](../standards/operations.md) (proposed): Even if Data Protection APIs aren't called by user code, data protection should be configured to create a persistent cryptographic key store: the ASP.NET Core Data Protection stack is used by several ASP.NET Core middlewares, including authentication middleware (for example, cookie middleware) and cross-site request forgery (CSRF) protections.
- [OPS-016](../standards/operations.md) (proposed): When a systemd unit runs a .NET app, avoid setting KillSignal=SIGINT: .NET lifetime integrations listen for SIGTERM to start a graceful shutdown.
- [OPS-017](../standards/operations.md) (proposed): If the /health and /alive endpoints are enabled outside Development, it's recommended to protect them with routing features such as host filtering or authorization.
- [SEC-007](../standards/security.md) (proposed): Every ASP.NET Core app sets a fallback authorization policy that requires a signed-in user, so an endpoint needs one unless it opts out with AllowAnonymous; only endpoints that must be public opt out (health probes, the Development OpenAPI document), each with a comment saying why, and a test pins that list.
- [SEC-008](../standards/security.md) (proposed): An app never stores passwords or issues its own access tokens: users sign in with an OpenID Connect provider (Microsoft Entra ID or Entra External ID unless an ADR picks another), and an HTTP API accepts its access tokens with AddJwtBearer, which checks their signature, issuer, audience and lifetime, set under Authentication:Schemes:Bearer; development uses dotnet user-jwts, whose key stays in user secrets; ASP.NET Core Identity or any other scheme needs an ADR.
- [SEC-009](../standards/security.md) (proposed): Every read or change of a user's data is limited to that user's data in the query itself, in the application and data layers, not only in the endpoint; the user's id is the token's sub claim, which the fallback policy requires (unique within one issuer, so an app that trusts more than one keys on the issuer and sub together), and another user's item answers 404, as one that doesn't exist does.
- [SEC-010](../standards/security.md) (proposed): Every value a client sends is checked where it enters the app against what's allowed: required fields, a maximum length for every string, URI and collection, and a range for every number. A value outside those bounds gets a 400 validation problem that names the field; a domain rule's refusal is a 400 Problem (API-006); neither repeats the value. API-006 says how a Minimal API does it.
- [SEC-011](../standards/security.md) (accepted): Every ASP.NET Core app applies Microsoft's Kestrel production security checklist for where it's hosted, at the edge or behind a proxy: HTTPS only (at the edge, Kestrel terminates TLS 1.2 or later and serves no plain HTTP; behind a proxy, the proxy does), host filtering with its own AllowedHosts, HSTS outside Development, a rate limit for each caller, CORS only for named origins, a request body cap well under the 30 MB default, and no Server header; behind a proxy, forwarded headers only from KnownProxies or KnownIPNetworks, and never through ASPNETCORE_FORWARDEDHEADERS_ENABLED.
- [SEC-017](../standards/security.md) (proposed): For a server-side app where most or all endpoints require authentication, set a fallback authorization policy that requires an authenticated user; it is secure by default and protects newly added endpoints. Apply AllowAnonymous to an endpoint that is intentionally public. ASVS 8.2.1: function-level access is restricted to consumers with explicit permissions.
- [SEC-020](../standards/security.md) (proposed): Define and enforce a maximum size of data on all incoming parameters and payloads, such as maximum length for strings, maximum number of elements in arrays and maximum upload file size. Add server-side validation for query string and request body parameters, especially the one that controls the number of records returned. ASVS 2.2.1 and 2.2.2: input is validated to enforce business or functional expectations for that input, which should either use positive validation against an allow list of values, patterns and ranges or compare the input to an expected structure and logical limits, and input validation is enforced at a trusted service layer.
- [SEC-021](../standards/security.md) (accepted): Where Kestrel is an edge server, with no reverse proxy: use host-filtering middleware, enable HTTPS redirection, rate limiting must be handled by the application, don't enable the Forwarded Headers middleware, and verify ASPNETCORE_FORWARDEDHEADERS_ENABLED isn't set in edge deployments. Behind a reverse proxy, the Forwarded Headers middleware is required; configure KnownProxies or KnownIPNetworks explicitly. For an API that doesn't accept large uploads, consider lowering the request body limit significantly. Disable Kestrel's Server header (AddServerHeader) to prevent server identification. OWASP API4: limit how often a client can interact with the API within a defined timeframe (rate limiting).
- [SEC-022](../standards/security.md) (accepted): Most applications should strive for OWASP ASVS Level 2; Level 1 contains the minimum requirements to consider when securing an application and is a critical starting point.
- [UI-001](../standards/ui.md) (proposed): Every UI an app ships meets WCAG 2.2 level AA: web UI (Blazor, Razor) as written, native UI (MAUI, desktop) as W3C's WCAG2ICT note applies it. Building UI, an agent checks at least the success criteria UI-003 lists, keeping each one's own exceptions, such as a link inside a sentence or a data table that needs two dimensions.
- [UI-002](../standards/ui.md) (proposed): Every page of a web UI (Blazor, Razor) has a Playwright test in the app's E2E.Tests project that opens it, checks it loaded, and runs axe's WCAG 2.2 level A and AA rules (the tags wcag2a, wcag2aa, wcag21a, wcag21aa and wcag22aa), failing on any violation; what a person does that axe can't see, such as where focus goes after a link or the first Tab, gets its own Playwright test.
- [UI-003](../standards/ui.md) (proposed): For WCAG 2.2 level AA conformance, a UI satisfies all the level A and level AA success criteria (or a level AA conforming alternate version is provided); among them, each with the exceptions and conditions WCAG lists: non-text content has a text alternative, and non-text content that is a control or accepts user input has a name that describes its purpose (1.1.1); information, structure and relationships conveyed through presentation can be programmatically determined or are available in text (1.3.1); color isn't the only visual means of conveying information (1.4.1); text has a contrast ratio of at least 4.5:1, and large-scale text at least 3:1 (1.4.3); text, except captions and images of text, can be resized without assistive technology up to 200 percent without loss of content or functionality (1.4.4); vertically scrolling content can be presented at a width equivalent to 320 CSS pixels without loss of information or functionality and without scrolling in two dimensions (1.4.10); the visual information required to identify user interface components and states has a contrast ratio of at least 3:1 against adjacent colors (1.4.11); all functionality is operable through a keyboard interface (2.1.1), and focus moved to a component with the keyboard can be moved away with the keyboard (2.1.2); where navigation sequences affect meaning or operation, components receive focus in an order that preserves meaning and operability (2.4.3); keyboard operable UI has a mode where the focus indicator is visible (2.4.7), and a component receiving focus isn't entirely hidden by author-created content (2.4.11); pointer targets are at least 24 by 24 CSS pixels (2.5.8); labels or instructions are provided when content requires user input (3.3.2); no step in authentication requires a cognitive function test unless that step provides an alternative or a mechanism WCAG lists (3.3.8); and every user interface component's name and role can be programmatically determined (4.1.2). W3C's WCAG2ICT note helps clarify how to use WCAG 2 for non-web software.

## Consequences

- A Blazor app gets the core ruleset, the web rules that name `blazor`, the BLZ component rules and the web UI accessibility rules (UI-001 to UI-003).
- All BLZ rules are proposed. BLZ-015 asks for Razor Pages Identity UI, which differs from the Blazor Web App template's own component-based Identity UI. The owner may want to keep it proposed.
- **Gap:** Many sentences in the Blazor pages had their API names stripped in the extract the helper read, so the batch left them out rather than quote them wrongly. The guidance they carry is not covered: async lifecycle methods returning Task, calling base-class lifecycle methods, disposing HttpClient, the InputFile size limit and EventCallback typing. The pages components/lifecycle, components/rendering and forms/binding have no rule. A follow-up pass with the local Markdown should read them.

## Pillars affected

- **Security:** CSP, XSS, prerender state and authorization rules (BLZ-011 to BLZ-014, BLZ-020).
- **Reliability:** disposal, error boundaries and render-mode rules (BLZ-001, BLZ-005, BLZ-019).
- **Performance Efficiency:** rendering and JS interop rules (BLZ-008 to BLZ-010).
- **Accessibility** (not a pillar): UI-001 to UI-003 apply.
