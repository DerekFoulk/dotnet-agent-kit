# ADR-0090: Blazor Hybrid ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A Blazor Hybrid app runs Razor components inside a native app's web view, here a .NET MAUI app. Its `project-types.yml` entry is `blazor-hybrid` (Blazor Hybrid (.NET MAUI)), and its docs start at <https://learn.microsoft.com/aspnet/core/blazor/hybrid/>. ADR-0008 allows Blazor Hybrid only by an ADR (ARC-004).

ADR-0082 makes every rule name the project types it applies to. ADR-0084 gives an app only the common ruleset plus the rulesets of its project types. This ADR records the ruleset for `blazor-hybrid` (Blazor Hybrid (.NET MAUI)), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/aspnetcore.md`):

- <https://learn.microsoft.com/aspnet/core/blazor/hybrid/class-libraries-best-practices>: never reference MAUI from a Razor class library of shared components (BLZ-026).
- <https://learn.microsoft.com/aspnet/core/blazor/hybrid/security/>: avoid authentication in the context of the web view (BLZ-027).
- <https://learn.microsoft.com/aspnet/core/blazor/hybrid/security/security-considerations>: treat code in the web view as untrusted (BLZ-028, BLZ-012).
- <https://learn.microsoft.com/aspnet/core/blazor/components/>: component design (shared with Blazor Web Apps) (BLZ-002, BLZ-003).
- <https://learn.microsoft.com/aspnet/core/blazor/components/component-disposal>: unsubscribe and dispose (BLZ-005).
- <https://learn.microsoft.com/aspnet/core/blazor/fundamentals/dependency-injection>: scoped services in components (BLZ-018).
- <https://learn.microsoft.com/aspnet/core/blazor/javascript-interoperability/>: JS interop (general) (BLZ-009).
- <https://learn.microsoft.com/dotnet/maui/data-cloud/database-sqlite>: local database for the MAUI host (MAU-001).
- <https://learn.microsoft.com/dotnet/maui/platform-integration/appmodel/permissions>: permissions in the MAUI host (MAU-012).

A Blazor Hybrid app gets both sets of rules that name it: the Blazor component rules (BLZ-002 to BLZ-009, BLZ-012, BLZ-018, BLZ-019 and BLZ-026 to BLZ-028, of which BLZ-027 and BLZ-028 name `blazor-hybrid` alone) and the MAUI host rules (MAU-001, MAU-004, MAU-005, MAU-007, MAU-008, MAU-011 to MAU-013, MAU-015 and MAU-016). The XAML-only MAUI rules don't apply, since the UI is components.

## Options

### Option 1: A ruleset for Blazor Hybrid (.NET MAUI)

- **Trade-offs:** An app of this type gets the common rules plus the rules that name `blazor-hybrid`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `projectTypes` list per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `projectTypes` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a desktop app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `blazor-hybrid` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the project-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

## The ruleset

Generated by Build-AgentRules.ps1 from docs/standards; proposed rules are marked, and aren't in force until the owner accepts them.

- [ARC-010](../standards/architecture.md) (proposed): In MAUI and desktop apps, view models and all other logic live in UI-independent libraries (ARC-003); a UI project, one that sets UseMaui, UseWPF, UseWindowsForms or UseWinUI, holds only views, platform code and startup wiring, no other project references it, and the coverage gate exempts it.
- [ARC-011](../standards/architecture.md) (proposed): A new general-purpose Windows desktop app is recommended to use WinUI 3, the native UI framework delivered with the Windows App SDK; a team expecting to target several platforms should start with .NET MAUI (Microsoft names React Native for Desktop beside it), which uses WinUI 3 when running on Windows.
- [ARC-014](../standards/architecture.md) (proposed): A new desktop app uses the framework ARC-011 names for its platforms (WinUI 3 for a Windows desktop app, .NET MAUI for several platforms); a new WPF or Windows Forms app needs an ADR that says why.
- [BLZ-002](../standards/blazor.md) (proposed): Avoid creating components that write directly to their own component parameters. Declare parameters as auto properties with no custom logic in their get or set accessors, and don't use the required modifier or an init accessor on them.
- [BLZ-003](../standards/blazor.md) (proposed): For two-way data binding, use @bind:get and @bind:set rather than an event handler. Don't specify a culture with @bind:culture on date and number field types.
- [BLZ-004](../standards/blazor.md) (proposed): Avoid thread-blocking calls in components. When a component must be updated from an external event, such as a timer or other notification, use InvokeAsync to dispatch the work to Blazor's synchronization context.
- [BLZ-005](../standards/blazor.md) (proposed): Always unsubscribe event handlers from .NET events, and always dispose objects a component creates on the .NET side to avoid leaking managed memory.
- [BLZ-006](../standards/blazor.md) (proposed): Prefer .razor files and let the compiler deal with sequence numbers; manual render tree builder logic is advanced and unsafe, and not recommended for general component development.
- [BLZ-007](../standards/blazor.md) (proposed): Avoid creating a single large class that represents the entire global application state; prefer granular classes cascaded separately, each with specific subscriptions, so only the components that use a portion of the state are affected when it changes.
- [BLZ-008](../standards/blazor.md) (proposed): Where rendering is expensive or measured to cause UI lag, avoid thousands of component instances, avoid attribute splatting for components that render at scale, avoid recreating delegates for many repeated elements or components, and don't trigger events too rapidly. Most components don't need this optimization.
- [BLZ-009](../standards/blazor.md) (proposed): Avoid inline event handlers in JavaScript that Blazor calls; assign handlers in JavaScript with addEventListener. Use JS collocation combined with JS modules, and avoid inline JavaScript. Dispose a JSObjectReference you hold to avoid leaking JS memory, and don't run JS interop for DOM cleanup tasks during component disposal or location changes. Avoid excessively fine-grained JS interop calls.
- [BLZ-012](../standards/blazor.md) (proposed): Avoid rendering raw HTML built from an untrusted source. Avoid passing user-supplied data in parameters to JavaScript calls (for example, don't write it to innerHTML), and avoid using user input as part of navigation call arguments.
- [BLZ-018](../standards/blazor.md) (proposed): Don't directly inject a scoped service into a component if you intend the service lifetime to match the lifetime of the component.
- [BLZ-019](../standards/blazor.md) (proposed): In production, don't render framework exception messages or stack traces in the UI. Narrowly scope error boundaries in most scenarios.
- [BLZ-026](../standards/blazor.md) (proposed): Never reference the MAUI library from a Razor class library that holds shared components. Such a library should be host-agnostic, not depending on specific hosting infrastructure or platform APIs, and prefer interfaces over abstract classes.
- [BLZ-027](../standards/blazor.md) (proposed): In a Blazor Hybrid app, avoid authentication in the context of the Web View: don't implement the authentication workflow yourself, don't use the Web View control to perform authentication, and avoid passing tokens to the document context (JavaScript).
- [BLZ-028](../standards/blazor.md) (proposed): In a Blazor Hybrid app, treat code inside the Web View as untrusted and validate anything that comes from it (events, JS interop). Don't store credentials, security tokens or sensitive user data in the Web View's context, and avoid loading content from a third-party origin. Establishing a CSP is recommended.
- [DAT-018](../standards/data.md) (proposed): In a platform-specific app that uses EF Core migrations (.NET MAUI or WinUI 3), store the migrations in a separate project, and don't use the platform-specific application project as the startup project for EF tools; prefer an AnyCPU migrations project.
- [HST-002](../standards/hosting.md) (proposed): Don't cache an HttpClient that IHttpClientFactory created for a long time, and don't inject a typed client into a singleton service: request a client in a timely manner or each time you need one. Don't cache scope-related information (such as data from HttpContext) inside HttpMessageHandler instances or their dependencies. Don't register a typed client separately, because AddHttpClient already registers it. Don't start a large number of HTTP/1.1 requests at once without specifying limits.
- [HST-003](../standards/hosting.md) (proposed): Name a log category after the fully qualified class that writes the message (an ILogger<T> does it), and use log message template formatting, not string interpolation. If a logging data store is slow, don't write to it directly from a logger.
- [MAU-001](../standards/maui.md) (proposed): Use the sqlite-net-pcl NuGet package for a local SQLite database in a .NET MAUI project. Microsoft.Data.Sqlite, a lightweight ADO.NET provider for SQLite, is the alternative the same page names.
- [MAU-004](../standards/maui.md) (proposed): When profiling a MAUI app, avoid profiling in a simulator, which may distort performance. Ideally profile on a variety of devices, and at a minimum on a device with the lowest anticipated specification.
- [MAU-005](../standards/maui.md) (proposed): Before a MAUI app displays its initial UI, it should provide a splash screen, and its activation logic should only perform the work needed to let the user start using the app.
- [MAU-007](../standards/maui.md) (proposed): In a MAUI app, update UI elements with data from asynchronous operations on the UI thread, to avoid exceptions. Avoid asynchronous constructors, and use the lazy task pattern to avoid waiting for asynchronous operations to complete during app startup. Blocking on a task and async void are STY-011's.
- [MAU-008](../standards/maui.md) (proposed): In a MAUI app, unsubscribe from events before the subscriber object is disposed of, to prevent memory leaks. On iOS and Mac Catalyst, avoid strong circular references.
- [MAU-011](../standards/maui.md) (proposed): Handle a MAUI window's lifecycle events as the page says. On Stopped, disconnect from long running processes and cancel pending requests that might consume device resources: the app may be terminated by the operating system and might not resume. On Resumed, subscribe to any required events and refresh the visible page's content. On Destroying, remove event subscriptions attached to the native window. On iOS and Mac Catalyst, persist string state to the Backgrounding event's State property. When overriding an Android activity lifecycle method the page lists, always call the super class's implementation.
- [MAU-012](../standards/maui.md) (proposed): In a MAUI app, don't request permissions from the MauiProgram or App class; request them only once the app's first page has appeared. Explain to the user why the app needs a permission (best practice). A permission must have its matching attributes in the Android Manifest and its matching string in Info.plist.
- [MAU-013](../standards/maui.md) (proposed): Authenticate a MAUI app through a web backend as a middle layer between the app and the authentication provider (the best practice). Older mobile-only authentication libraries and patterns that don't use a web backend are strongly recommended against, because they can't store client secrets securely. On Apple platforms, an app that uses any social login service must also offer Sign in with Apple, according to Apple's review guidelines as the page relays them.
- [MAU-015](../standards/maui.md) (proposed): Don't build new messaging on MessagingCenter, which is deprecated: replace it with WeakReferenceMessenger from the CommunityToolkit.Mvvm package, or use events with weak references for simple scenarios.
- [MAU-016](../standards/maui.md) (proposed): When a MAUI app is deployed with Native AOT on iOS or Mac Catalyst, review and correct all trimming and AOT warnings; all binding expressions must use compiled bindings; the $(PublishAot) build property shouldn't be conditioned by build configuration. Develop, debug and test as usual and publish with Native AOT as one of the last steps.
- [SUP-011](../standards/supply-chain.md) (proposed): Workloads such as MAUI install at the workload set whose version is the SDK's own (dotnet workload restore --version with the version dotnet --version prints), never the latest.
- [UI-001](../standards/ui.md) (proposed): Every UI an app ships meets WCAG 2.2 level AA: web UI (Blazor, Razor) as written, native UI (MAUI, desktop) as W3C's WCAG2ICT note applies it. Building UI, an agent checks at least the success criteria UI-003 lists, keeping each one's own exceptions, such as a link inside a sentence or a data table that needs two dimensions.
- [UI-003](../standards/ui.md) (proposed): To meet WCAG 2.2 level AA, a UI must meet, among all the other level A and AA success criteria: a text alternative for non-text content, and a name for every control (1.1.1); structure and relationships that can be programmatically determined (1.3.1); color not as the only visual means of conveying information (1.4.1); a contrast ratio of at least 4.5:1 for text, 3:1 for large text (1.4.3); text resizable to 200 percent without loss of content or functionality (1.4.4); content that reflows at a width equivalent to 320 CSS pixels (1.4.10); a contrast ratio of at least 3:1 for the visual information that identifies user interface components and states (1.4.11); all functionality operable through a keyboard interface (2.1.1) with no keyboard trap (2.1.2); a focus order that preserves meaning and operability (2.4.3); a visible keyboard focus indicator (2.4.7) that isn't entirely hidden by author-created content (2.4.11); pointer targets at least 24 by 24 CSS pixels unless an exception applies (2.5.8); labels or instructions where content requires input (3.3.2); no cognitive function test in authentication unless an alternative or a mechanism is offered (3.3.8); and a programmatically determinable name and role for every user interface component (4.1.2). For native UI, W3C's WCAG2ICT note says how each criterion applies.

## Consequences

- A Blazor Hybrid app gets the common ruleset, the component rules, the MAUI host rules and UI-001 and UI-003. It gets no web server rules, since it hosts no web server.
- The rules are proposed.
- **Gap:** Microsoft has only three pages written for Blazor Hybrid itself (class libraries, security, security considerations). The rest of its guidance is Blazor's general pages, which this ruleset reuses.

## Pillars affected

- **Security:** the web view is untrusted code, and authentication stays out of it (BLZ-027, BLZ-028).
- **Reliability:** lifecycle and disposal rules (BLZ-005, MAU-008, MAU-011).
- **Performance Efficiency:** rendering and startup rules (BLZ-008, MAU-005).
