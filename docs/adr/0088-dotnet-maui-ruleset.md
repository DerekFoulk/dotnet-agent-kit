# ADR-0088: .NET MAUI ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A .NET MAUI app is a native app for Android, iOS, macOS and Windows, built with XAML and C#. Its `app-types.yml` entry is `maui` (.NET MAUI), and its docs start at <https://learn.microsoft.com/dotnet/maui/what-is-maui>.

ADR-0084 makes every rule name its `scope`, `core` or the app types it applies to, and gives an app only the core ruleset (ADR-0085) plus the rulesets of its app types. This ADR records the ruleset for `maui` (.NET MAUI), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/maui.md`):

- <https://learn.microsoft.com/dotnet/maui/data-cloud/database-sqlite>: use sqlite-net-pcl for a local SQLite database; Microsoft.Data.Sqlite is the named alternative (MAU-001).
- <https://learn.microsoft.com/dotnet/maui/fundamentals/data-binding/compiled-bindings>: set x:DataType; compiled bindings (MAU-002).
- <https://learn.microsoft.com/dotnet/maui/fundamentals/accessibility>: semantic properties are the recommended approach (UI-004).
- <https://learn.microsoft.com/dotnet/maui/deployment/performance>: profile on devices, splash screen, UI thread updates, unsubscribe events, resources (MAU-004 to MAU-009).
- <https://learn.microsoft.com/dotnet/maui/user-interface/layouts/>: do not nest ScrollViews; bindable layouts for small collections (MAU-010).
- <https://learn.microsoft.com/dotnet/maui/fundamentals/app-lifecycle>: handle Stopped, Resumed and Destroying (MAU-011).
- <https://learn.microsoft.com/dotnet/maui/platform-integration/appmodel/permissions>: request permissions after the first page, with an explanation (MAU-012).
- <https://learn.microsoft.com/dotnet/maui/platform-integration/communication/authentication>: authenticate through a web backend (MAU-013).
- <https://learn.microsoft.com/dotnet/maui/fundamentals/shell/navigation>: always await GoToAsync; IQueryAttributable (MAU-014).
- <https://learn.microsoft.com/dotnet/maui/fundamentals/messagingcenter>: MessagingCenter is deprecated; use WeakReferenceMessenger (MAU-015).
- <https://learn.microsoft.com/dotnet/maui/deployment/nativeaot>: fix all trimming and AOT warnings (MAU-016).

MAUI's own local-database guidance is the page at <https://learn.microsoft.com/dotnet/maui/data-cloud/database-sqlite>: use the sqlite-net-pcl package (MAU-001). It never mentions EF Core. DAT-002 and DAT-005, the EF Core server-database rules, name `web-api` and `blazor`, not `maui`, so they don't apply to a MAUI app. DAT-018 (a separate migrations project) names `maui` for an app that picks EF Core anyway.

The kit's own MAUI rules stay: ARC-010 (logic in UI-independent libraries), ARC-017 (view models and views independent) and SUP-011 (workload sets).

ARC-011 and ARC-014 cover the choice of a desktop UI. ARC-011 is the kit's preference: a desktop app is a .NET MAUI app, since WinUI 3, WPF and Windows Forms aren't supported app types yet (ADR-0084), so ADR-0059's choice of .NET MAUI for desktop apps stands. ARC-014 holds Microsoft's recommendation for a new Windows desktop app. Blazor Hybrid isn't a supported app type yet either, so the MAU rules name `maui` alone.

## Options

### Option 1: A ruleset for .NET MAUI

- **Trade-offs:** An app of this type gets the core rules plus the rules whose scope names `maui`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `scope` per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `scope` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a .NET MAUI app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `maui` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the app-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

## The ruleset

Generated by Build-AgentRules.ps1 from docs/standards; proposed rules are marked, and aren't in force until the owner accepts them.

<!-- ruleset: maui -->
- [ARC-010](../standards/architecture.md) (proposed): In MAUI and desktop apps, view models and all other logic live in UI-independent libraries (ARC-003); a UI project, one that sets UseMaui, UseWPF, UseWindowsForms or UseWinUI, holds only views, platform code and startup wiring, no other project references it, and the coverage gate exempts it.
- [ARC-011](../standards/architecture.md) (proposed): A desktop app is a .NET MAUI app (Windows and Mac Catalyst), the same stack as mobile: WinUI 3, WPF and Windows Forms aren't supported app types yet, so a desktop app on any of them, like any other app type the kit doesn't support, needs an ADR.
- [ARC-014](../standards/architecture.md) (proposed): A new general-purpose Windows desktop app is recommended to use WinUI 3, the native UI framework delivered with the Windows App SDK; a team expecting to target several platforms should start with .NET MAUI (Microsoft names React Native for Desktop beside it), which uses WinUI 3 when running on Windows.
- [ARC-017](../standards/architecture.md) (proposed): In a .NET MAUI app that uses MVVM, keep view models and views independent: don't reference view types, such as Button and ListView, from view models. Avoid enabling and disabling UI elements in the code-behind: enable and disable them by binding to view model properties instead.
- [DAT-018](../standards/data.md) (proposed): In a platform-specific app that uses EF Core migrations, such as a .NET MAUI or WinUI app, storing the migrations in a different project from the one containing the DbContext is recommended. Don't use the platform-specific application project as the startup project for EF tools, and prefer an AnyCPU migrations project.
- [MAU-001](../standards/maui.md) (proposed): When a .NET MAUI app uses SQLite-net for a local SQLite database, as Microsoft's MAUI local database page does, use the sqlite-net-pcl NuGet package, despite the package name.
- [MAU-002](../standards/maui.md) (proposed): In .NET MAUI XAML, setting the x:DataType attribute at the same level in the view hierarchy as the BindingContext is set is recommended, and adding x:DataType to all elements where the binding context changes is best practice. Consider changing the compiled-binding warnings, such as XC0022 and XC0023, to build errors with the $(WarningsAsErrors) build property; XC0022 and XC0023 are always suppressed unless $(MauiStrictXamlCompilation) is true.
- [MAU-004](../standards/maui.md) (proposed): Avoid profiling a MAUI app in a simulator, as the simulator may distort the app's performance. Ideally, profiling should be performed on a variety of devices, and at a minimum on a device that has the lowest anticipated specification.
- [MAU-005](../standards/maui.md) (proposed): Before a MAUI app displays its initial UI, it should provide a splash screen, and its activation logic should only perform the work needed to let the user start using the app.
- [MAU-006](../standards/maui.md) (proposed): Resources used throughout a MAUI app should be stored in the app's resource dictionary to avoid duplication. XAML that's specific to a page shouldn't be included in the app's resource dictionary, because it is then parsed at app startup instead of when a page needs it; a resource used by a page that isn't the startup page should be placed in that page's resource dictionary.
- [MAU-007](../standards/maui.md) (proposed): In a MAUI app, update UI elements with data from asynchronous operations on the UI thread, to avoid exceptions. Avoid asynchronous constructors, and use the lazy task pattern to avoid waiting for asynchronous operations to complete during app startup. Blocking on a task and async void are STY-011's.
- [MAU-008](../standards/maui.md) (proposed): In a MAUI app, events should be unsubscribed from before the subscriber object is disposed of, to prevent memory leaks. Avoid strong circular references on iOS and Mac Catalyst.
- [MAU-009](../standards/maui.md) (proposed): In MAUI XAML, don't use bindings for content that can easily be set statically, and don't reproduce a layout's appearance with combinations of other layouts. Images should only be created when required and should be released as soon as the app no longer requires them.
- [MAU-010](../standards/maui.md) (proposed): In a MAUI layout, ScrollView objects should not be nested, and should not be nested with other controls that provide scrolling, such as CollectionView, ListView and WebView. Avoid using the AbsoluteLayout.AutoSize property whenever possible, as it makes the layout engine perform additional layout calculations. Bindable layouts should only be used when the collection of items to be displayed is small, and scrolling and selection aren't required.
- [MAU-011](../standards/maui.md) (proposed): In a MAUI window's lifecycle events: on Stopped, disconnect from any long running processes, or cancel any pending requests that might consume device resources, because there's no guarantee the app will resume (the operating system may terminate it). On Resumed, subscribe to any required events and refresh any content that's on the visible page. On Destroying, remove any event subscriptions attached to the native window. On iOS and Mac Catalyst, any string state should be persisted to the State property of the Backgrounding event's BackgroundingEventArgs. In the Android activity lifecycle overrides that need it, such as OnPause and OnDestroy, always call the super class's implementation.
- [MAU-012](../standards/maui.md) (proposed): In a MAUI app, permissions shouldn't be requested from the MauiProgram or App class, and should only be requested once the first page of the app has appeared. It's best practice to explain to the user why the app needs a specific permission. On Android, permissions must have the matching attributes set in the Android Manifest file; on iOS and Mac Catalyst, permissions must have a matching string in the Info.plist file.
- [MAU-013](../standards/maui.md) (proposed): Using a web backend as a middle layer between a MAUI app and the authentication provider is the best practice. Older mobile-only authentication libraries and patterns that don't use a web backend in the authentication flow are strongly recommended against, due to their inherent lack of security for storing client secrets. An Apple app that uses any social login service to authenticate must also offer Sign in with Apple as an option (Apple's review guidelines).
- [MAU-014](../standards/maui.md) (proposed): In a MAUI Shell app, always await the GoToAsync method. Receiving navigation data using the QueryPropertyAttribute isn't trim safe and shouldn't be used with full trimming or NativeAOT; instead, types that need to accept query parameters should implement the IQueryAttributable interface. Setting an explicit AccessibilityLabel is recommended whenever IconOverride is set or TextOverride is hidden.
- [MAU-015](../standards/maui.md) (proposed): MessagingCenter has been deprecated in .NET MAUI: replacing it with WeakReferenceMessenger from the CommunityToolkit.Mvvm NuGet package is recommended, or using events with weak references for simple scenarios.
- [MAU-016](../standards/maui.md) (proposed): When building a MAUI app for Native AOT deployment on iOS or Mac Catalyst, you should review and correct all trimming and AOT warnings; all binding expressions must use compiled bindings, rather than a binding path that's set to a string; and the $(PublishAot) build property shouldn't be conditioned by build configuration. You should develop, debug and test the app as usual, and publish the final app with Native AOT as one of the last steps.
- [SUP-011](../standards/supply-chain.md) (proposed): Workloads such as MAUI install at the workload set whose version is the SDK's own (dotnet workload restore --version with the version dotnet --version prints), never the latest.
- [UI-001](../standards/ui.md) (proposed): Every UI an app ships meets WCAG 2.2 level AA: web UI (Blazor, Razor) as written, native UI (MAUI, desktop) as W3C's WCAG2ICT note applies it. Building UI, an agent checks at least the success criteria UI-003 lists, keeping each one's own exceptions, such as a link inside a sentence or a data table that needs two dimensions.
- [UI-003](../standards/ui.md) (proposed): For WCAG 2.2 level AA conformance, a UI satisfies all the level A and level AA success criteria (or a level AA conforming alternate version is provided); among them, each with the exceptions and conditions WCAG lists: non-text content has a text alternative, and non-text content that is a control or accepts user input has a name that describes its purpose (1.1.1); information, structure and relationships conveyed through presentation can be programmatically determined or are available in text (1.3.1); color isn't the only visual means of conveying information (1.4.1); text has a contrast ratio of at least 4.5:1, and large-scale text at least 3:1 (1.4.3); text, except captions and images of text, can be resized without assistive technology up to 200 percent without loss of content or functionality (1.4.4); vertically scrolling content can be presented at a width equivalent to 320 CSS pixels without loss of information or functionality and without scrolling in two dimensions (1.4.10); the visual information required to identify user interface components and states has a contrast ratio of at least 3:1 against adjacent colors (1.4.11); all functionality is operable through a keyboard interface (2.1.1), and focus moved to a component with the keyboard can be moved away with the keyboard (2.1.2); where navigation sequences affect meaning or operation, components receive focus in an order that preserves meaning and operability (2.4.3); keyboard operable UI has a mode where the focus indicator is visible (2.4.7), and a component receiving focus isn't entirely hidden by author-created content (2.4.11); pointer targets are at least 24 by 24 CSS pixels (2.5.8); labels or instructions are provided when content requires user input (3.3.2); no step in authentication requires a cognitive function test unless that step provides an alternative or a mechanism WCAG lists (3.3.8); and every user interface component's name and role can be programmatically determined (4.1.2). W3C's WCAG2ICT note helps clarify how to use WCAG 2 for non-web software.
- [UI-004](../standards/ui.md) (proposed): In a .NET MAUI app, semantic properties are the recommended approach to providing accessibility values; automation properties, the Xamarin.Forms approach, have been superseded by them, and AutomationProperties.Name and HelpText have been deprecated since .NET 8. Description should be set on elements that have a meaning that's important for understanding the content or interacting with the user interface; avoid setting it on a Label, or on an Entry or Editor on Android. Ensure images and icons have alternate text descriptions; support large fonts and high contrast (avoid hardcoding control dimensions and prefer layouts that resize to accommodate larger font sizes, and test color schemes in high-contrast mode); design the visual tree with navigation in mind; don't rely on audio or color cues alone; and test the accessibility features of the app on each platform it targets.

## Consequences

- A MAUI app gets the core ruleset, the MAU rules, the desktop and mobile rules whose scope names `maui` (ARC-010, ARC-011, ARC-014, ARC-017, SUP-011, DAT-018, UI-001, UI-003, UI-004) and no web or EF Core server rules.
- MAU-001, MAU-002 and MAU-004 to MAU-016 are proposed. MAU-003 was removed as a duplicate of UI-004.
- MAU-013's Apple Sign In requirement is Apple's rule as the MAUI page relays it. The batch didn't check Apple's current guidelines.
- **Gap:** The inventory's maui page marks some pages out of scope (custom handlers, single-control API pages, IDE and CLI how-tos); a later pass may read some of them.

## Pillars affected

- **Reliability:** lifecycle, permission and event-unsubscribe rules (MAU-008, MAU-011, MAU-012).
- **Security:** web-backend authentication and permission rules (MAU-012, MAU-013).
- **Performance Efficiency:** compiled bindings, layout and startup rules (MAU-002, MAU-005, MAU-009, MAU-010).
- **Cost Optimization:** not affected.
