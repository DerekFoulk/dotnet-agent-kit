# ADR-0094: Console and Worker Service ruleset

- **Status:** Proposed
- **Date:** 2026-11-17

## Context

A console app or Worker Service is a .NET app with no UI: a command-line tool, or a long-running host for background services. Its `project-types.yml` entry is `console-worker` (Console app or Worker Service), and its docs start at <https://learn.microsoft.com/dotnet/core/extensions/workers>.

ADR-0082 makes every rule name the project types it applies to. ADR-0084 gives an app only the common ruleset plus the rulesets of its project types. This ADR records the ruleset for `console-worker` (Console app or Worker Service), and what Microsoft's own guidance says for it.

Microsoft's guidance pages for this type, as the 2026-11-17 inventory found them (the full list, with every page's verdict, is in `docs/inventory/dotnet.md`):

- <https://learn.microsoft.com/dotnet/standard/commandline/design-guidance>: options give parameters to commands; do not use them to specify actions (CS-037).
- <https://learn.microsoft.com/dotnet/core/extensions/dependency-injection/auto-activation>: no scoped or transient auto-activation (HST-001).
- <https://learn.microsoft.com/dotnet/core/extensions/logging/overview>: category names; message templates; no slow-store writes (HST-003).
- <https://learn.microsoft.com/dotnet/core/extensions/caching>: AddDistributedMemoryCache only in development or testing (HST-004).
- <https://learn.microsoft.com/dotnet/core/extensions/httpclient-factory-troubleshooting>: HttpClient factory DO NOTs (HST-002).
- <https://learn.microsoft.com/dotnet/core/resilience/http-resilience>: one resilience handler (NET-002).
- <https://learn.microsoft.com/aspnet/core/host-and-deploy/iis/>: a background-only app is a Windows Service, not IIS (OPS-014).
- <https://learn.microsoft.com/aspnet/core/host-and-deploy/linux-nginx>: avoid KillSignal=SIGINT in a systemd unit (OPS-016).
- <https://learn.microsoft.com/ef/core/managing-schemas/migrations/applying>: bundles or scripts; expand, migrate, contract (DAT-013, DAT-014).

Console and worker apps share the hosting rules (HST-001 to HST-004, NET-002), the shutdown and settings rules (OPS-005, OPS-006, OPS-009) and EF Core's server-database rules with the web types. CS-037 and OPS-014 name `console-worker` alone. They get no web security, UI or accessibility rules.

## Options

### Option 1: A ruleset for Console app or Worker Service

- **Trade-offs:** An app of this type gets the common rules plus the rules that name `console-worker`. Nothing that belongs to another type reaches it, so an agent reads fewer rules and none that don't apply. The cost is one `projectTypes` list per rule, which `Test-RuleSources.ps1` checks.
- **Reversibility:** Easy. A rule's `projectTypes` can be widened or narrowed in one edit, and the generated files follow.
- **Risk:** Low. A rule listed for too few types is missed by the apps it should reach. Code review and the ruleset block below make that visible.

### Option 2: Every app gets every rule

This is how the kit worked before 2026-11-17.

- **Trade-offs:** One list, nothing to maintain per type. But web assumptions leak into other types (health endpoints, Problem Details, Kestrel checks in a desktop app), and an agent reads rules that don't apply and has to decide which to ignore.
- **Reversibility:** Easy.
- **Risk:** Medium. Rules that don't apply get ignored, and then the ones that do get ignored with them.

## Recommendation

Option 1: it gives a `console-worker` app the rules written for it and keeps the rest out of its way.

## Decision

Option 1, proposed on 2026-11-17 as part of the project-type rulesets (ADR-0084). The owner accepts it with the rules it lists.

- [CS-037](../standards/csharp.md) (proposed): In a command-line app, make options provide parameters to commands rather than specify actions, avoid using the common .NET CLI aliases differently than their usual meaning, and be consistent in pluralization of option names.
- [DAT-002](../standards/data.md) (proposed): An app with a server relational database reaches it through EF Core, and its schema changes only through EF Core code-first migrations kept in the repo, never EnsureCreated (tests apply the migrations too, DAT-005); a test fails when the model has changes no migration covers.
- [DAT-005](../standards/data.md) (proposed): Integration and functional tests of an app with a server database, and its local development, run against the production database engine, in a container (Testcontainers for tests) or its official emulator (the Azure Cosmos DB emulator), with the app's migrations applied; never the EF Core in-memory provider, and never SQLite standing in for another engine.
- [DAT-013](../standards/data.md) (proposed): Use expand -> migrate -> contract schema changes to keep old and new app versions compatible during a transition.
- [DAT-014](../standards/data.md) (proposed): For automated deployment of EF Core migrations, use a migration bundle; use a SQL script instead when the SQL must be reviewed, modified, archived, or handed to a DBA before it is applied. Applying migrations at runtime needs careful consideration in production, and a bundle is preferred for automation and a SQL script where review and approval are required; don't make every application replica run migrations from its entrypoint. Use a separate identity for deployment that has permission to change the schema, so the identity the application uses at run time should normally have only the permissions to read and write data, and don't store production connection strings in source control or embed them in the bundle.
- [NET-002](../standards/dotnet.md) (proposed): When adding resilience to an HTTP client, add only one resilience handler and avoid stacking handlers; to combine several strategies, consider the AddResilienceHandler extension method.
- [HST-001](../standards/hosting.md) (proposed): Don't auto-activate services with a scoped or transient lifetime, and keep what an auto-activated service does at startup fast. For longer-running initialization, consider background services or hosted services.
- [HST-002](../standards/hosting.md) (proposed): Don't cache an HttpClient that IHttpClientFactory created for a long time, and don't inject a typed client into a singleton service: request a client in a timely manner or each time you need one. Don't cache scope-related information (such as data from HttpContext) inside HttpMessageHandler instances or their dependencies. Don't register a typed client separately, because AddHttpClient already registers it. Don't start a large number of HTTP/1.1 requests at once without specifying limits.
- [HST-003](../standards/hosting.md) (proposed): Name a log category after the fully qualified class that writes the message (an ILogger<T> does it), and use log message template formatting, not string interpolation. If a logging data store is slow, don't write to it directly from a logger.
- [HST-004](../standards/hosting.md) (proposed): Use AddDistributedMemoryCache only in development or testing; it isn't a viable production implementation of IDistributedCache.
- [OPS-005](../standards/operations.md) (accepted): An app shuts down gracefully: on SIGTERM its host stops taking requests and gives in-flight work a shutdown timeout that ends before the platform's grace period (25 seconds where the platform allows 30, Kubernetes' default), and long-running work stops on the host's stopping token or the request's cancellation token, which every call passes on.
- [OPS-006](../standards/operations.md) (accepted): An app's settings are options validated when it starts (ValidateDataAnnotations or a validator, and ValidateOnStart), so bad configuration stops it at startup instead of failing requests later.
- [OPS-009](../standards/operations.md) (accepted): An app with long-running operations that need to finish gracefully should subscribe to the host's ApplicationStopping event, which the host signals when it receives a shutdown signal such as SIGTERM.
- [OPS-014](../standards/operations.md) (proposed): If an app only hosts background services, avoid IIS hosting and use a Windows Service to host it.
- [OPS-016](../standards/operations.md) (proposed): When a systemd unit runs a .NET app, avoid setting KillSignal=SIGINT: .NET lifetime integrations listen for SIGTERM to start a graceful shutdown.

## Consequences

- A console or worker app gets the common ruleset and the rules that name `console-worker`.
- The rules from the 2026-11-17 pages (CS-037, OPS-014, OPS-016, HST-001 to HST-004, NET-002) are proposed.
- **Gap:** Microsoft's Worker Services page (<https://learn.microsoft.com/dotnet/core/extensions/workers>) and its generic host page scored 0 and 1 for guidance wording in the inventory, so no rule comes from them. Worker-specific guidance is thin: the rules above come from hosting, command-line and deployment pages.

## Pillars affected

- **Reliability:** shutdown, hosting and resilience rules (OPS-005, OPS-009, NET-002).
- **Operational Excellence:** logging, settings and migration rules (HST-003, OPS-006, DAT-014).
- **Cost Optimization:** not affected.
